Orchestrator on Notion

The store is four linked Notion databases. Each action of a session, the supervisor or you becomes a short, fixed sequence of Notion calls: a body document, then an event row that links the parties and the body. This page traces each sequence, step by step.

A read uses the cache; a write reads Notion first

Read

  1. Each database has a cache in the process.
  2. After 2 s, one query reads the rows edited in the last 2 minutes. Notion keeps the edit time to the minute.
  3. The feed reads Events with Ms after the last event minus 2 minutes, sorted by Ms.
  4. A body text is read once from its source block and kept.

Write

  1. Query the row by its title.
  2. An add of a row that exists: refuse. A change of a row that changed after the read: refuse. Nothing is written.
  3. Create or update the row.
  4. After a create: query again. Two rows with one title: the oldest wins, the other writer archives its row.

Many sessions share the databases with five rules

  1. One writer each session. The lease row in Docs says who writes now: a live chat or a supervisor turn.
  2. One supervisor each store. Two supervisors would start the same turn two times.
  3. One inbox each party. Each event has one To. Your inbox is the user row.
  4. The first answer wins. The claim row of a thread refuses the second answer.
  5. A tree of sessions. An orchestrator spawns children; each child row has Parent.
