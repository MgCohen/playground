Orchestrator on Notion

All parties talk through one stream of messages. With a notion: store, that stream and all other state live in four linked Notion databases, so local and cloud sessions share them. The supervisor on your computer reads the stream and starts the session turns.

Four flows do the work

A question and its answer

sequenceDiagram
  participant W as Worker
  participant N as Notion
  participant U as You
  participant S as Supervisor
  W->>N: orch post question (Bodies, then Events)
  S->>N: feed read (each 2 s)
  S-->>U: card in UI and in your inbox row
  U->>N: answer (claim, then Events)
  S->>N: feed read: answer to worker
  S->>W: turn with the answer

The first answer in a thread wins: a claim row in Docs. A second answer is refused.

A child session starts

sequenceDiagram
  participant O as Orchestrator
  participant N as Notion
  participant S as Supervisor
  participant C as Child
  O->>N: spawn child: Sessions row (Parent), brief event
  S->>N: feed read: brief to child
  S->>C: start turn (local or cloud)
  C->>N: report done
  S->>O: turn with the report

The brief says where: local or cloud. Only the provider knows how to start it.

No answer in time: a default

sequenceDiagram
  participant S as Supervisor
  participant N as Notion
  participant W as Worker
  participant G as GitHub
  S->>N: open question, wait time ended
  S->>N: answer by the policy level
  S->>W: turn with the default answer
  W->>G: work as a stacked draft PR
  S-->>N: review request to you

You review the default later: approve, change or refuse.

One store call

flowchart TD
  A[orch or supervisor call] --> B{Read or write?}
  B -->|read| C{Cache older than 2 s?}
  C -->|no| D[Answer from cache]
  C -->|yes| E[Query rows edited in last 2 min] --> D
  B -->|write| F[Read the row again]
  F --> G{Exists or newer?}
  G -->|yes| H[Refuse: nothing written]
  G -->|no| I[Create or update row] --> J[Read again: oldest row wins]

Notion has no conditional write. The read before and after a write closes most races.

Many sessions share one stream with five rules

  1. One writer for each session. The lease row says who writes now: your live chat or a supervisor turn. The supervisor waits while a live chat holds it.
  2. One supervisor for each store. Two supervisors would start the same turn two times. A second store needs its own Notion page.
  3. One inbox for each party. Each message has one receiver. Your inbox is the user row in Sessions.
  4. The first answer wins. A claim row for each thread refuses the second answer.
  5. A tree of sessions. Each child has a Parent. A root orchestrator owns its tree and its stream id.
