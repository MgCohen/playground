What Blazor gives us for events and navigation

Each row on this page comes from a measurement in spikes/blazor-nav/09-official or 10-events (.NET 10, Blazor Server, headless Chromium). The question: can the official event mechanisms be the base of our pipeline, in place of the JS interop that we built?

Events can carry the pipeline, but they do not do it better. Spike 10 runs the same push and back on an event channel with no IJSRuntime call. The times are the same to the ms: 349 ms to the end of the view transition in both modes.

The event channel loses the error path. A JS error gives no event, so only a C# time limit ends the wait (2007 ms). IJSRuntime gives the error and its message in 14 ms.

The channel is our own RPC on top of events: ids, phases, an outlet and an observer. IJSRuntime already gives these. The one gain is a command with more than one result phase.

Events are the right tool for what the browser starts: clicks, gestures, the end of a motion that C# did not start. Calls are the right tool for what C# starts.

Open questions

  • The data is from headless Chromium. The tray host (WebView2 with our own WebViewManager) is not measured.
  • Should the input trace use the custom click event, and should the self-test Press wait for its trace line?
  • Should PageDepth move to HistoryEntryState? Tab links give no state, so a tab change still needs the path.
