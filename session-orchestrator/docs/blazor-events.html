What Blazor gives us for events and navigation

Each row on this page comes from a measurement in spikes/blazor-nav/09-official or 10-events (.NET 10, Blazor Server, headless Chromium). The question: can the official event mechanisms be the base of our pipeline, in place of the JS interop that we built?

Events can carry the pipeline, but they do not do it better. Spike 10 runs the same push and back on an event channel with no IJSRuntime call. The times are the same to the ms: 349 ms to the end of the view transition in both modes.

The event channel loses the error path. A JS error gives no event, so only a C# time limit ends the wait (2007 ms). IJSRuntime gives the error and its message in 14 ms.

The channel is our own RPC on top of events: ids, phases, an outlet and an observer. IJSRuntime already gives these. The one gain is a command with more than one result phase.

Events are the right tool for what the browser starts: clicks, gestures, the end of a motion that C# did not start. Calls are the right tool for what C# starts.

A worked example from the spike code, cut down. One app with two pages: Home and Deep. A click on Home opens Deep with a slide (a view transition), then the blocks of Deep rise one after the other. The snippets are from spikes/blazor-nav/10-events and 09-official.

The parts

Browser JS + CSS

  • The DOM that Blazor renders
  • motion.css: the keyframes
  • {Assembly}.lib.module.js: registers custom events, runs the view transition and the settle wait

Blazor runtime official

  • Event dispatch: a DOM event to a C# handler
  • NavigationManager: NavigateTo, the changing handlers, HistoryEntryState
  • The router: renders the page of the URL after all handlers end
  • IJSRuntime: a C# call to a JS function, with its Promise

Our C# components

  • MainLayout: the one changing handler (direction, motion)
  • Pages: Home, Deep (the enter wait in OnAfterRenderAsync)

Components/Pages/Deep.razor

@inject IJSRuntime JS

<div class="page" id="deep">
    <h1>Deep <button @onclick="Back">Back</button></h1>

@code {
    protected override async Task OnAfterRenderAsync(bool firstRender)
    {
        if (!firstRender) return;
        // The DOM is there and the CSS animations have started (7 of 7 probes in spike 09).
        var r = await JS.InvokeAsync<Waited>("lab.wait", "#deep .blocks", 2000);
        // r.By is "end", "cancel" or "limit". Now the page is ready for input.
    }

    Task Back() => JS.InvokeVoidAsync("lab.back").AsTask();   // history.back()

    sealed record Waited(string By, int Ms);
}

A page is a component. @onclick is an official event: Blazor sends the DOM click to the C# method on the circuit.

2. A simple custom event

A custom event has three parts. This one is the click trace of spike 09: one handler at the layout root sees each click.

Lab/EventHandlers.cs: the C# side

public sealed class TracedClickArgs : EventArgs
{
    public string Test { get; set; } = "";   // data-test of the clicked element
    public double At { get; set; }           // performance.now() in the browser
}

// The C# name "ontracedclick" must differ from the browser event "click".
[EventHandler("ontracedclick", typeof(TracedClickArgs), enableStopPropagation: true, enablePreventDefault: true)]
public static class EventHandlers;

wwwroot/Spike.Official.lib.module.js: the browser side

export function afterWebStarted(blazor) {     // Blazor loads this file by its name
  blazor.registerCustomEventType("tracedclick", {
    browserEventName: "click",                 // the DOM event to listen to
    createEventArgs: e => ({                   // the JSON that becomes TracedClickArgs
      test: e.target.closest?.("[data-test]")?.dataset.test || "",
      at: performance.now(),
    }),
  });
}

Components/Layout/MainLayout.razor: the use

<div class="frame" @ontracedclick="Clicked">
    @Body
</div>

@code {
    void Clicked(TracedClickArgs e) => Trace.Add($"click {e.Test} at {e.At:0} ms");
}

Measured: each click arrived with its data-test, also when a button stopped onclick with :stopPropagation. The handler runs after the handler of the button.

3. Navigation

Home.razor: the move, with a state on the history entry

<button @onclick='() => Nav.NavigateTo("deep",
    new NavigationOptions { HistoryEntryState = "depth=1" })'>Open deep</button>

MainLayout.razor: the one changing handler

IDisposable? changing;

protected override void OnAfterRender(bool firstRender)
{
    if (firstRender) changing = Nav.RegisterLocationChangingHandler(Changing);
}

static int Depth(string? s) => s is { } v && v.StartsWith("depth=") ? int.Parse(v[6..]) : 0;

async ValueTask Changing(LocationChangingContext c)
{
    // c.HistoryEntryState = the target entry, Nav.HistoryEntryState = the current entry.
    // Both are correct also on the browser back and forward buttons.
    var kind = Depth(c.HistoryEntryState) > Depth(Nav.HistoryEntryState) ? "push" : "back";

    // A guard step goes here: if (dirty) { c.PreventNavigation(); return; }

    // The router waits until this handler ends. A second move cancels c.CancellationToken.
    await JS.InvokeVoidAsync("lab.begin", c.CancellationToken, kind);   // returns at "captured"
}

public void Dispose() => changing?.Dispose();

Rules from the data: use one handler, with the steps in order in it. Two handlers (or a handler and NavigationLock) run at the same time. NavLink gives no state, so a tab link has depth 0.

4. A simple animation

wwwroot/motion.css: the slide and the rise

.vt::view-transition-old(root) { animation: out-left 300ms ease-out both; }
.vt::view-transition-new(root) { animation: in-right 300ms ease-out both; }
@keyframes out-left { to { transform: translateX(-30%); opacity: 0; } }
@keyframes in-right { from { transform: translateX(100%); } }

.blocks > div { animation: rise 300ms ease-out both; }
.blocks > div:nth-child(2) { animation-delay: 80ms; }
.blocks > div:nth-child(3) { animation-delay: 160ms; }
@keyframes rise { from { transform: translateY(16px); opacity: 0; } }

lib.module.js: the view transition, in two phases

function begin(kind) {
  const root = document.documentElement;
  root.classList.add("vt");
  root.classList.toggle("vt-back", kind === "back");
  let captured;
  const c = new Promise(r => { captured = r; });
  // The callback runs after the browser has the picture of the old page.
  // It resolves "captured", then waits for the next DOM change (the router render).
  const t = document.startViewTransition(() => { captured(); return rendered(); });
  const finished = t.finished.then(() => root.classList.remove("vt", "vt-back"));
  return { captured: c, finished };
}

lib.module.js: the settle wait (why a raw animationend is not enough)

function settle(el, limitMs) {
  return new Promise(resolve => {
    setTimeout(() => resolve({ by: "limit" }), limitMs);        // nothing moves forever
    requestAnimationFrame(() => {
      // All finite animations of the element and its children: 3 for the 3 blocks.
      const all = el.getAnimations({ subtree: true })
        .filter(a => a.effect.getComputedTiming().endTime !== Infinity);
      if (all.length === 0) { resolve({ by: "end" }); return; }  // no motion: no event would come
      Promise.all(all.map(a => a.finished)).then(() => resolve({ by: "end" }),
                                                () => resolve({ by: "cancel" }));
    });
  });
}

Measured: animationend fires one time for each block (3 events) and never when nothing moves. The settle wait gives one answer in each case.
