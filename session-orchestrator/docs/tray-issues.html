Tray Issue Tracker

The known problems of the tray, one tab for each. Each issue has its own page: pick it in the list. We discuss one issue at a time.

What this page is for

One record for each problem. Each record shows the proof, the cause and the proposed fix. We stop at each issue and decide together. This stops the loop of fixes for problems that nobody proved.

Working rule

  1. When you or a test find a problem, write a record. Do not fix it.
  2. Try to reproduce it one time. If the reproduction or the error is clear, add the proof.
  3. If it is not clear after one try, record what was tried and stop.
  4. You pick which issue we work on, and when.

Reason: one cause can make many issues, and one issue can have many causes. We see this only when all records are side by side. A fix loop on one issue hides that.

ReportedDetectedReplicatedNot real
What

I2 · The empty frame detector gives false alarms

ReportedDetectedReplicatedFixed
What

empty.py marks a frame as empty when its mean color is within 0.6 of the backdrop mean. A frame with the tray can have the same mean.

Proof

The two strips on I1: both marked frames show the tray. 5 of 5 marks in base-now are near a sheet motion.

Replicate
strip.ps1 -Gif base-now.gif -Times base-now.gif.times.txt -Nth 1..5
Cause

Known. One mean value for the full frame cannot tell "no tray" from "tray with a different shade".

Proposal

Change the rule: a frame is empty when almost all pixels in the tray area have the backdrop color.

empty  = share of pixels with color #CCCCCC (±3) in the panel area > 98 %
record = that share for each frame, in place of the mean

Proof that the new rule works:

  1. The old open blink (the real one, see F1) still gives an empty frame.
  2. The base-now run gives 0.
Decision
Question

Do I change the detector to the pixel share rule, and test it on the old and new runs?

I3 · A stress step that misses does not fail the run

ReportedDetectedReplicatedFixed
What

If a press finds no element, the run logs "no element" and continues. The frame count then covers steps that did not occur.

Proof
# base-now/stress.txt, cycle 1
14:59:05.670 .acts [data-act="left"]: no element .acts [data-act="left"]
14:59:06.573 .presence .scrim: no element .presence .scrim
# 46 presses clicked, 2 missed. Run h-sheet: the same misses in cycle 1.
Cause

Known. Act writes the result but has no pass rule. In cycle 1 the Cards page is not ready 700 ms after the tab click.

Proposal
  1. Wait for the element with Until before the press, up to 3 s.
  2. Count the misses. Exit 1 if one press misses.

I7 · The badge hover cuts the ring at the left

ReportedDetectedReplicatedFixed
What

At a hover, the badge tab extends to the left with the counts. The left part of the tab, with the ring, is cut off.

Proof
FAIL badge-hover-fits: tab width at the hover 333 CSS px,
     click area of the hover 280 (+ 14 margin), window 332;
     text "4 questions · 1 review · 2 reports · 1 blocked"
Replicate
Orchestrator.Tray --selftest out     # check badge-hover-fits: FAIL
Cause

Known. Two sizes do not agree:

  • CSS: the hover width is width: auto, so the text sets it. With this text it is 333 px.
  • C#: the click area of the hover is fixed at 280 + 14 px. The window region is the click area, and Windows also clips the drawing to it.

The result: 39 px at the left are cut. The window (332 px) is also 1 px too narrow.

Proposal
OptionChangeEffect
ACSS: hover width fixed at 280 px (the spec N1 value); the text ends with "…" if it is too longOne size in two places. Long counts are cut
BThe page sends its tab width to C#; the click area and the window follow itNo text cut. More code, and the window size changes
CA shorter text: "4 q · 1 rev · 2 rep · 1 blk"Fits now, but a large count can still overflow

The check badge-hover-fits proves the fix. It is in the self-test now and fails.

Decision
Question

Which option: A, B or C? Recommendation: A, because the spec gives 280 px and the size stays in one token.

I9 · Eight motion mechanisms, no single flow

ReportedDetectedReplicatedFixed
What

Proof

Fact of the code, from the review on the view architecture page (Findings tab). No reproduction needed.

Known. Each mechanism was added for one feature. No shared rule for start and wait.

ReportedDetectedReplicatedFixed

ReportedDetectedReplicatedFixed
What

Proposal

One wait helper for all: settle, with a log line when the limit ends a wait.
