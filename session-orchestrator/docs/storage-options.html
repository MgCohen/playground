Orchestrator Storage Options

Recommendation: keep the files as the store. Fix the full stream copy (B2-9) with an index, and move the store out of the git checkout.

A database or Notion as the store adds a network, an account or a new write path for the plugin hooks. None of the needs today requires it.

Cloud workers and the phone reach the store through the supervisor HTTP API and the tunnel. Notion can be a one-way mirror later.

The real cost is in the reads, not the storage

  • B2-9: FileStore.Report and FileStore.OpenDecisions copy the full stream for each session at each tick.
  • Each new orch process reads all envelope files at its first query. Each session runs orch often, and the stream grows by about 2,000 files a day.
  • A database fixes both, but an index and a day cache in the files fix both too.

A. Files as today, with an index fix

The envelope files stay the source. EventStream gets an index by session. A day cache file holds the envelopes of each closed day, so a new process reads one file for each day. The contract permits a cache that the stream can make again.

B. SQLite on this PC

One file in WAL mode gives indexes and transactions. The plugin hooks have no SQLite access, so each hook write must start orch post or call the supervisor. A .NET process start costs about 0.2 s for each of 2,000 writes a day. A call to the supervisor fails while the supervisor is down.

C. Hosted database

Postgres (for example Neon or Supabase) or Cloudflare D1. It gives direct access from the cloud, but G1 already sends cloud workers through the supervisor API. D1 has no C# driver: the code calls its HTTP API or a Worker. Each write takes a network trip, and the PC stops when the network stops.

D. Notion as the store

Notion has no transaction, no exclusive create and no change push. The first answer rule and the cursor lock cannot work. The trace volume is above the rate limit at peak.

E. Notion as a mirror

A supervisor reactor subscribes to report, question, answer and review. It writes one row for each in a Notion database, from a queue with retry. Notion never writes back. The phone already gets the cards through the tunnel, so the mirror gives search and history only.

Triggers for a database (S5)

  • A tick or a cold orch query takes more than 1 s after S1 and S2.
  • The stream holds more than 100,000 envelopes in the open days.
  • Two PCs must write one store.

If a trigger fires, SQLite behind IStreamBackend comes first. The plugin hooks keep their file writes into events/, and the supervisor moves them into the database. So the hooks stay fast.

Rules for each step

  1. Change docs/store.md in the same commit as a store file.
  2. Keep each cache one that the stream can make again.
  3. Test with a scratchpad ORCH_STORE, never with store/.

Non-goals

  • No direct store access for cloud workers. Reason: one writer path keeps the lease and claim rules in C#.
  • No Notion writes into the store. Reason: Notion has no atomic create, so the first answer rule breaks.
  • No migration of version 1 stores. Reason: store.md rule 4.
