Devices plan: Android, web and Linux

Each client uses the same Razor components. Android and Linux need a new host and three shared refactors, not a UI rewrite. Cloud visual tests run the components in headless Chromium. The Windows native parts keep their own self-test.

Kinds of work

Host

Same code. A different start or a different browser.

Wrapper

The same running app inside a native shell.

New host

The same components in a new native project, plus shared refactors.

Rewrite

A new UI technology. No shared UI code.

Web, full · works today

The web host serves the full UI to each browser. A settings portal is more pages in the same host.

  • Blazor Server keeps a live connection. A mobile network drop shows the reconnect screen.
  • Remote access (tunnel, sign-in) is out of scope for this plan.
Android, installable web app · smallest step

Chrome on Android installs the web UI as an app icon with its own window. The UI code does not change.

  • Add a web manifest, a service worker and icons.
  • Check touch, safe areas and the keyboard on a real phone.
  • The microphone works only on HTTPS.
  • Limit: no offline mode, because Blazor Server needs the server.
Android, WebView app · a store package

A thin native shell (for example a Trusted Web Activity) opens the installable web app. It gives a Play Store package and native notices.

  • Needs the installable web app first.
  • The UI still runs on the server.
Android, native MAUI app · the full app

.NET MAUI Blazor Hybrid runs the components on the phone, inside the Android WebView. This is the Android form of the tray host.

  • Needs refactors R1 to R4.
  • The phone has no store and no claude, so all data comes over the HTTP API.
  • The Win32 parts have no Android form. Android uses its own notices instead of the ball and the edge tab.
  • Toolchain: the MAUI Android workload, the Android SDK and a signing key.
Linux tray · optional third native host

WinForms and WebView2 run only on Windows. A Linux tray needs a new host, for example Photino (WebKitGTK) or Electron (Chromium).

  • The ball, the edge tab, the grow shadow and the drag become new X11 or GTK code.
  • Photino renders with WebKit, not Chromium. Its screens do not match the Windows tray.
  • A cloud VM has no display, so a Linux tray also needs a virtual display (Xvfb).

Proposed order

  1. Installable web app on Android (manifest, service worker, icons).
  2. R1 and R3: Razor class library and host interfaces.
  3. Cloud visual tests in headless Chromium with the tray frame.
  4. R2 and R4, then the MAUI Android host.
  5. Linux tray: only if the cloud tests are not enough.

Non-goals

  • No server, tunnel or sign-in work in this plan. Reason: the user scoped this plan to the app.
  • No Kotlin or Flutter app. Reason: it duplicates all UI code.
