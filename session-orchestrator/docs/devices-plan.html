Devices plan: Android, web and desktop

Spike A1 shows that the Razor components run unchanged in an Android app. The plan makes one shared UI library in the VSA shape (one presenter for each module), then three hosts on it: web, Windows tray and Android. Each phase has a check that shows it is done.

P1b · Presenters and requests · Board goes away
Goal
The UI has the VSA shape: a view uses the presenter of its module, and a presenter sends requests.
Shape
One presenter for each module (table above). Each read or action of Board becomes one request with one handler in the slice of its module. The handlers keep the logic of Board.
Sender
One IRequestSender. The local sender calls the handlers in the process. A later remote sender sends the same requests over HTTP; then the phone needs no store.
Push
A presenter listens to StreamHub.Changed and raises its own Changed. The views render on it.
Calls
About 60 call sites in the views change from Board.X to the presenter of the module. The calls become async.
Reference
vsa-template/docs/presenter-events.md. Copy the shape, not the packages.
Done when
No Board class. Tests, tray self-test and the Android smoke test pass. One unit test for each handler.

P6 · Phone host features · small native parts
  • The Android back button goes back in the app. It must not close the app.
  • The status bar band has the theme color, not white.
  • The microphone: test speech.js on a real phone. If it fails, add native speech through a host interface.
  • Optional: an Android notice for a new waiting card.

Rules for all phases

  • Components use no server-only and no Windows-only code. A function that differs between hosts goes behind a host interface, as IWidgetWindow.
  • A new view goes into the folder of its module, with its presenter.
  • Each phase is one PR. The next phase waits for the review.

Non-goals

  • No VSA framework packages. Reason: the decision "plain .NET until VSA 1.0" stays. The UI copies only the shape.
  • No change to the logic of the components. Reason: A1 shows that they work on Android as they are.
  • No backend work: no tunnel, no sign-in, no remote data. Reason: a separate plan covers the server.
  • No Play Store release. Reason: one user; an APK file is enough.
