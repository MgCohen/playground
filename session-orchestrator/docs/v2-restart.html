V2 Visual Restart

The app looks correct, but each visual fix costs too much. This page states the goal of the restart, what we know today, and the eleven root causes of the pains. The target design is on the V2 Target Design page.

Purpose

Goal

Rebuild the view of the app (web UI and tray) from scratch. Use one data flow and one design system, so that a visual change is a small, local change.

Why now

The visuals work, but 28 tracker issues and 88 architecture gaps came from the same few causes. Each fix found the next defect. The R1 and R2 refactors came only after many single fixes.

I look for
  • The root causes of the pains, not the list of defects.
  • The parts that cause the most work for each visual change.
  • What to keep: the look, the motion spec, the R1 and R2 lessons.
  • What to take from a library or a design system, and what to write.
I know
  • The look and the motion are approved (I6, V7, E2). They are the reference, not the problem.
  • The data model is ready: view.json gives the document and the preview of each kind.
  • The tray has two windows (spike S7). Their faults come from the native host, not from the split.
  • Details: tab 2 · Current state.

Expected outcome

  • A new view project that renders all 7 pages and the tray from one view model.
  • Each fact has one owner: a token, a record or a state. Copies are not possible.
  • Each state change is an event, so the trace and the tests read events, not pixels and timers.
  • The old app stays until the new app passes the parity check of each slice.
