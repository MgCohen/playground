Session Orchestrator Design

One local supervisor controls many Claude Code sessions through a shared file store. Each session has one writer at a time, so a session moves between the desktop app and the supervisor with no lost message. Decisions go to the user as free-text cards: a default applies after a timeout by risk level, and each default lands as a stacked draft PR that the user reviews later.

All parts talk through the store, never directly
flowchart LR
  U[User: phone or desktop] -->|answers, reviews| UI[Phone UI]
  UI -->|HTTP| SV[Supervisor]
  SV -->|reads, writes| ST[(Store: files)]
  M[Mod in each session] -->|reads, writes| ST
  SV -->|Agent SDK turn| S1[Session, holder supervisor]
  M --- S2[Session, holder live]
  S2 --- APP[Desktop app or Remote Control]
  APP --- U

A live lease counts as live while its heartbeat or the lease is less than 15 s old. After that, the supervisor releases it. The mod writes a heartbeat every 3 s on its own timer.

Two code sessions in one folder share one working tree and break each other's branches. Give each code session its own git worktree. The supervisor does not make worktrees yet: see Build, milestone M3.

Start a session tree

  1. Send POST /api/sessions with a title, a folder and a brief.
  2. The supervisor writes meta.json and inbox/1.txt.
  3. The next tick starts a new SDK session with that id.
  4. The session calls spawn_child for each piece of parallel work.
  5. Each child runs in its own SDK turn, up to maxRuns at one time.
  6. A child calls report with done or blocked.
  7. The supervisor writes that report to the inbox of the parent.

Policy levels

The levels are data in store/policy.json. You set how many levels, the definition, the timeout and the docs check of each. The session picks a level from the definitions.

LevelTimeoutDocs checkExample
low30 minYesA name or a file place
medium4 hYesA design choice that a review can undo
highNeverNoHard to undo, outward actions

An unknown level counts as the strictest level. A decision with no default always waits for the user.

Each default is one draft PR on top of the one before it
flowchart LR
  M[main] --> P1[PR 1: decision A]
  P1 --> P2[PR 2: decision B]
  P2 --> P3[PR 3: decision C]

Review verdicts

VerdictSession doesStack above
approveMarks the PR ready, no mergeStays
changeCommits the change on that branchRebased on the change
refuseCloses the PR, keeps the branchClosed, rebuilt from the base

After a refuse, the session starts again from the base branch in the new direction. It reuses commits from the closed branches where they still fit. Each answer, default and review is an event in the stream (today: one line in store/ledger.jsonl).

Question rules

  • The user answers in free text or by voice. Options are suggestions only.
  • A deny rule removes the built-in click question tool from all sessions.
  • In a normal session, the model asks in its reply text.
  • In an orchestrator session, the model calls ask_user.
Each message is a filled template: one schema, one text, one card
flowchart LR
  S[Sender: session, user, supervisor] -->|fields| V[core: validate]
  V -->|ok| F[Store file, JSON]
  F --> R[render.md: text for a session]
  F --> C[UI card for the user]
  V -->|error| E[Sender fixes the fields]

A sender never writes free text into the store. It fills the fields of a template. core validates the fields against the schema of the template, and refuses a message with a missing field. Then each reader shows the same data in its own way: a session gets text from render.md, and the phone UI draws the card of that template.

A report needs an action from the reader: the work is done or blocked. An update needs no action: it only shows progress, so the UI shows it in the session tree and not in the decision queue.

Event stream

Each message and each change of state is also an event in one stream. Nothing is lost: a reader picks what it needs with a query.

One stream records everything; each reader filters it

Stream rules

  • Write each event as one new file: store/events/<day>/<id>.json. Two writers never write one file, so no line gets lost.
  • Never change or delete an event. A correction is a new event with a refs link.
  • core writes the event first, then the state file of the session. The state files are for fast reads; the stream is the record.
  • The ledger of today is a query: the events with by = docs or policy, and the review events.
  • From M6, the supervisor can build the state files again from the stream after a crash.
orch events --since 3h                       # timeline of the last 3 hours
orch events --kind decision,report --open    # what needs the user
orch events --session eae5b144 --follow      # one session, live

Four problems: the mod and the supervisor each have their own copy of the store rules. The texts to the sessions are in the code. There is no command-line tool. There are no agent, skill or template files, so each brief repeats the instructions.

Open questions

  • Language of the orch command: Node, the same as the supervisor? Recommendation: yes, Node 26 with no build step.
  • Package layout: npm workspaces in one package.json? Recommendation: yes.
  • Schema format: JSON Schema with a small validator in core, or plain TypeScript checks? Recommendation: JSON Schema, because the UI and the tools can read the same file.
  • Plugin imports: can a hook import a relative .ts file? Recommendation: a small spike at the M0 start. If not, keep one file and generate it.
  • Plugin skills and agents: does CLAUDE_CODE_PLUGIN_DIRS give them to the session? Recommendation: a small spike at the M2 start.
  • Tunnel: which tool, and which sign-in? Recommendation: Cloudflare Tunnel with Cloudflare Access.
  • Worktrees: does the supervisor make them? Recommendation: yes, and it records the folder in meta.json.
  • Store: files, or SQLite? Recommendation: files until M5 shows a real problem.
  • Docs check for medium: keep it on? Recommendation: keep it.
  • Swipe meaning on a card? Recommendation: right accepts the default, left opens the free-text answer.
  • Delete the old folder claude-orchestrator? Recommendation: yes, after the next app restart.
