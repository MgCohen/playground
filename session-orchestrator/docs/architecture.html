Orchestrator architecture

The orchestrator is a set of vertical slices around one event stream. Each state change is an event, each read model is a projection, and each external system has one port. Architecture tests in NUnit make the code obey these rules.

Why this page exists

The code follows an architecture that is not written down in one place. The rules are in AGENTS.md, docs/plan.md and docs/decisions.md. The tests cover only some of them.

Example of the risk. The plan said: each provider call goes through one interface, IProvider. The sessions made an adapter interface for each feature: ITurnRunner, IDocsChecker, IStateChecker. No test refused it.

Proposal: vertical slices around the event stream

A modular monolith. The kernel holds the event stream and the ports. Each feature is one slice. The hosts only compose the parts and map input to slice commands.

Only the hosts reference Store and Providers. A slice cannot see an implementation, so it cannot make its own adapter.

All slices are in one project, Orchestrator.Features, with one folder and one namespace for each slice default K-Q2. The compiler does not separate the slices; the ArchUnitNET slice rule does.

You can delete a projection and build it again from the stream. The session registry, claims, decisions and workflow runs are projections.

The supervisor dispatches, the slices react default K-Q5

Web/Program.cs (composition root)
  services.AddSlice<Decisions>()      // registers its handlers, projections, reactors
  services.AddSlice<Sessions>()
  ...
Supervisor tick (host)
  read new events from the stream
    for each projection : apply(event)
    for each reactor    : react(event) -> command
  emit a Tick event        // timers: defaults, reminders, watchdog

The tick has no feature logic. A timer rule (default after 600 s, a reminder) is a reactor on the Tick event in its own slice.

State outside the stream: one short list default K-Q1

StateStoreReason
Lease and heartbeatIRepository (local)Write every 3 s
Subscription cursorsIRepository (local)Read position, not a fact
LogsILogSinkText for people, not state
Definitions (templates, modes, policy)IRepositorySource files in git

All other state comes from the stream. A claim is an append with an expected version, so the first writer wins.

Open questions

Answer in free text. Each answer goes into the Topology tab, and its question leaves this tab.

Q7 · Plain .NET or the VSA framework? open

Contextdocs/plan.md says: plain .NET until 1.0, decide after the VSA 0.1.0 release. The kernel copies IRepository from vsa-template.

Options(a) Plain .NET, with copied kernel parts. (b) Use the vsa-template packs.

Recommendation: (a). The plan decision stays. This page uses only the VSA ideas.

Q8 · How do we move the code? open

Options(a) One large move. (b) Slice by slice. The tests start with an allow list of known breaks, and each move removes items from it.

Recommendation: (b). Each step is small, and the allow list shows the progress.

Q9 · Where is the plugin in the topology? open

ContextThe plugin hooks (TypeScript) write store files from inside Claude Code.

Options(a) The live side of Providers/ClaudeCode. It writes only events, through the store contract. (b) A separate host with its own rules.

Recommendation: (a). Then rule A1 also covers the plugin.
