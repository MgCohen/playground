Advanced Features

The advanced features of the orchestrator UI: the features after the basic sessions, cards and event stream. The first set is three pages: a workflow run, the PR stack of a stream, and one PR. They connect through the stream: a stream has sessions, workflow runs and PRs. Each feature has the same parts: what it is, its logic, its capabilities and its workflow. More features come later as new tabs. The sketches come after the approval.

Design rules

  • Each page shows first what waits for you, then the state, then the history.
  • Each act on a page calls an existing command or API: orch run step, /api/decisions/…/review, orch merge. The page adds no new logic.
  • The store is the source. A page never reads GitHub or git as its source of truth. A live read is only a detail. The one exception is F14: its subject is GitHub (Q11).
  • Each page works in the 350 px widget frame. A wide frame shows more columns.
  • Each feature has at least one dedicated view. The sketches give each view 2 or 3 variants. A part of a view is a block on that view, not a feature.
F1 · summary

Stream bar

One bar at the top of each of the three pages, and of the session page. It names the stream and gives three tabs with counts. A badge shows the number of items that wait for you in this stream.

flowchart LR
  B["Stream C · 2 wait for you"] --- T1["Sessions 4"] --- T2["Runs 1"] --- T3["PRs 5"]
Logic
  • The page gets the stream id from its object: a session entry (stream), a run (through its owner), a PR (through its session).
  • Sessions: /api/sessions?stream=C, the same as orch tree --stream C.
  • Runs: the runs whose owner is in the stream.
  • PRs: the stack versions of the sessions of the stream.
  • "Waits for you": open questions with needs to the user, PRs in state open with no review, PRs that are ready to merge.
  • An object with no stream shows no bar.
Capabilities

Show

  • Stream code
  • Counts of sessions, runs, PRs
  • Count of items that wait for you

Do

  • Open a tab: a filtered list
  • Open the first item that waits for you
F2 · summary

Workflows

The workflow definitions and their runs. A definition is a graph of steps. A run is one execution of a definition, with an owner session and a goal. A step run is one pass of a run through one step. The main page is the run page: it shows the progress, the graph with the current step, the next steps and the history. When the run waits for you, the page shows the wait first and lets you act on it.

PR page

One PR with all the facts for a verdict: the task, the session that did it, the diff summary, the tests, and the questions that the policy answered with a default. The review buttons are at the bottom, in the page bar.

F5 · Status and analytics

Summary

A status page that gives the full picture. The top shows the current state. Under it, charts show how each number goes up and down over the last hours and days.

Capabilities

  • Now: open sessions by state (running, idle, stale, forgotten, not responding)
  • Now: open questions, PRs that wait for a review, runs that wait
  • Errors in the last hour and day: turn.fail, delivery.blocked, blocked, state.conflict, merge.block
  • Trends: each number over time, with up and down markers
  • Filter by project and by stream
  • Tap a number: the list of items behind it

Logic

  • Each number is a query of the event stream and the registry. No new record
  • A trend is a count by hour or by day of one envelope kind or one state change
  • When a kind of error repeats more than usual, the page marks the rise

Data

  • have envelopes, state.json history, registry
  • gap a count API by kind and by time bucket
  • gap a cache, so that the page does not read all days each time

F7 · Timers and stale reminders

Summary

Reminders for items that nobody touched for a long time. Today only questions (10 min, then 60 min) and forgotten sessions get reminders. F7 gives the same rule to each item that waits.

Capabilities

  • Stale PR: open, with no review for N hours
  • Stale run: in a wait for N hours
  • Stale session: idle with no report, or done and not archived
  • Stale stream: no envelope for N days
  • A timer that you set on an item: "remind me in 2 hours"
  • A "stale" badge on each page, and a list on the status page (F5)
  • Snooze and dismiss

Logic

  • The age of an item is the time since its last envelope
  • The limits are settings, as the reminders setting is today
  • One reminder for each stale episode, as forgotten.json does today. A new envelope starts a new episode
  • The watchdog of the supervisor checks the limits on each tick

Data

  • have question reminders, forgotten, archive-reminder
  • gap limits for PRs, runs and streams
  • gap a timer record and a snooze record

F14 · GitHub overview

Summary

One page with the GitHub state of each repository that the sessions work in: open issues, open PRs, recent merges, and the commit and CI status of each branch. It shows also the GitHub work that no session made.

Capabilities

  • Issues: open, new this week, with labels and the session that works on it
  • PRs: open, draft, ready, review asked, with the [orch] tag
  • Merges: the last merges into the base branch
  • Commit status: the CI result of the head of each open branch (pass, fail, running)
  • Filter by project (F6) and by stream
  • Link each item to its session or its PR page (F4) when one exists
  • Start a session for an issue

Logic

  • The repositories come from work.repo of the registry entries, and later from the project records (F6)
  • A PR in the store and the same PR on GitHub show as one row. The store gives the session and the review state; GitHub gives the CI and the comments
  • GitHub is a call into another system, not a model provider. So it needs no IProvider
  • A cache with a short age keeps the GitHub calls few

Data

  • have pr.open, pr.merge envelopes, the PR URL in reports
  • gap issues, CI status and comments: only on GitHub
  • gap a GitHub reader with a cache (Q11)
F15 · Change log

Summary

One page that tells what changed, newest first, grouped by day. It shows the result of the work, not the work: merged PRs, decisions that apply, new workflow versions and app releases. You read it to catch up after a pause.

Capabilities

  • One entry for each change: time, kind, title, project, stream, session, link
  • Kinds: PR merged, decision applied (answer, default, review verdict), workflow version, app release
  • Filter by project (F6), stream, kind and date
  • "Since my last visit" mark
  • Export one period as Markdown, for example for release notes
  • Each entry opens its PR page (F4), decision or run (F2)

Logic

  • The page reads the envelopes of the store. It writes nothing. A change log is a filtered view of the event stream
  • Only finished changes show: a merge, not an open PR; an applied decision, not an open question
  • The merge entry takes its text from the PR title and the report summary

Data

  • have pr.merge, decision and review envelopes, docs/decisions.md
  • gap task PRs that merge outside orch merge (P-G4)
  • gap workflow versions (P-G14) and an app release record

Open questions

Answer in the chat. Start the answer with answer:.

Q1. Which PRs show on the PR stack page?

The store records only decision PRs. Task PRs from gh pr create are not in the store.

Options: (a) decision PRs only; (b) decision PRs and task PRs, with a new record (P-G4); (c) all PRs, read live from GitHub.

Recommendation: (b). The stack shows the real work, and the store stays the source.

Q2. Do I sketch a full stream page too?

The brief names three pages. No stream page exists.

Options: (a) only the stream bar on each page; (b) the bar plus one small stream page.

Recommendation: (a). The stream page is a "Later drafts" item of ui-drafts.html.

Q3. How does the run page measure progress?

Loops make "3 of 6" vague.

Options: (a) visited steps of the total; (b) done steps on the shortest path to a done step, plus a loop count.

Recommendation: (b). It stays correct after a loop.

Q4. Which PRs can you merge on the stack page?

Options: (a) only the lowest ready PR; (b) any ready PR; (c) also "merge all ready".

Recommendation: (a), through orch merge. The other PRs show why they wait.

Q5. Which frame do the sketches use?

The drafts use the 350 px widget frame.

Options: (a) widget only; (b) widget plus one wide variant for each page.

Recommendation: (b). A diff and a stack are easier to read on a wide page.

Q6. Is PR review a workflow definition?

The rules of F3 and F4 fit the step format of C2. As a workflow, the PR page becomes a run page with a PR view.

Options: (a) no, keep the review rules in orch; (b) yes, sketch the pages for it and record it as a roadmap item.

Recommendation: (b) as a record only. The sketches show the PR page both ways.

Q8. What is the unit inside a project, for a big feature?

A project is a repository. A big feature has many sessions and PRs. The C1 stream already groups many sessions.

Options: (a) the stream is that unit: project → stream → task; (b) a new unit, for example "initiative", between project and stream; (c) the stream stays free, and a project is only a filter.

Recommendation: (a). It adds no new term, and the stream already has its id on each session and envelope.

Q9. Can one stream span more than one project?

Multi-project work (F8) puts the sessions of one feature in different repositories.

Options: (a) yes: a stream has one main project, and can hold sessions of other projects; (b) no: one stream for each project, and a link between the streams.

Recommendation: (a). The work is one piece, and the stream bar shows it in one place.

Q10. Does the session status page (F13) join the first set?

The run page and the PR page link to the session page. Today that page does not show runs, PRs or the registry.

Options: (a) yes: sketch it with F2–F4; (b) no: keep it in the backlog.

Recommendation: (a). Without it, the links from the new pages open a page with little data.

Q13. What does the change log (F15) show?

Proposal: the finished changes of the work (merges, applied decisions, workflow versions, app releases), for each project and stream. Other options: only the release notes of the orchestrator app, or a feed of all events.

Q11. Where does the GitHub data of F14 come from?

Issues and CI status are only on GitHub. The design rule says that the store is the source.

Options: (a) a live read with gh and a short cache, at page open; (b) the supervisor copies the GitHub state into envelopes on a timer; (c) GitHub webhooks through the tunnel (D1).

Recommendation: (a) first. It needs no new store kind. (b) can follow when F5 and F7 need GitHub history.
