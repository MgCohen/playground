Orchestrator Internals

How to use the orchestrator, and how it works today. Each tab has one topic. Start with the tutorial.

Tutorial: three scripts in a project "foobar"

Three worked examples with the same small job: make hello.ps1, add.ps1 and today.ps1. Each example uses a different way in. The commands are PowerShell.

ExampleWay inSessionsYou learn
1Terminal (orch) and the web UI1 workerStart, watch, answer a question, send more work, archive
2Terminal (orch)1 root and 3 workersSplit work, worktrees, child reports, review, merge
3A chat in the Claude Code appAnyLet a chat session drive orch for you, open a supervisor session in the app

Before each example

A
Terminal 1

Make the project folder and its git repository.

mkdir $HOME\Documents\Projects\foobar; cd $HOME\Documents\Projects\foobar
git init -b main
"# foobar`n`nRules: one script for each job. Each script has a comment line at the top." | Set-Content AGENTS.md
git add .; git commit -m "Start foobar"
B
Terminal 2, keep it open

Start the supervisor. It runs the tick loop, the API and the UI on port 7777.

cd $HOME\Documents\Projects\playground\session-orchestrator
dotnet run --project src/Orchestrator.Web
C
Terminal 1

Check the setup. Each line must say ok.

orch doctor

Open http://127.0.0.1:7777/ in a browser. Keep it next to the terminal.

Example 1 One worker, from the terminal and the UI
1
Terminal 1

Start a worker session. The brief tells it the job, and it also tells it to ask you one question.

orch new --title "foobar scripts" --agent worker `
  --skills orch-ask,orch-report,orch-stack `
  --goal "Make three PowerShell scripts: hello.ps1 prints a greeting, add.ps1 adds two numbers, today.ps1 prints the date. Before you write add.ps1, ask the user if it takes the numbers as arguments or from a prompt (risk medium, default: arguments). Commit each script." `
  --done-when "The three scripts are committed and each one runs."

The command prints the session id, for example 3f2a9c1e-…. It only writes files. In the next 3 s, the supervisor starts the first turn.

2
Terminal 1 or the UI, tab Sessions

Watch the work. A short id prefix is enough.

orch tree                          # all sessions and their state
orch status 3f2a                   # one session: turn, report, decisions, stack
orch events --session 3f2a --follow   # each event as it comes
3
The UI, tab Queue, or Terminal 1

The worker asks its question, then ends its turn. The question shows in the Queue. Answer it there in free text, or in the terminal.

orch decisions
toolu_01Ab… [medium, default arguments] foobar scripts: Does add.ps1 take the numbers as arguments or from a prompt?
orch answer toolu_01Ab "Arguments. Show a usage line if there are not two numbers."

The next tick starts a turn with your answer. If you do not answer, the policy applies the default after 4 h (level medium). The worker then puts that work on its own branch orch/decision-toolu_01Ab, and the Queue asks you to review it.

4
Terminal 1

When the worker reports done, check the result in the repository.

orch status 3f2a
git log --oneline
.\add.ps1 2 3
5
Terminal 1, or the send box of the session card

Give the same session more work. It keeps its context.

orch send 3f2a "Add a README.md that lists the three scripts with one example each."
6
Terminal 1, or the Archive button

When the work is done, archive the session. The supervisor never runs it again.

orch archive 3f2a

Use orch stop 3f2a to pause a session, and orch resume 3f2a to continue it.

Example 2 A root session that splits the work into three workers
1
Terminal 1

Start a root session with the agent orchestrator. The brief gives the split, the merge permission and the merge command. The steps come from this brief and from the agent prompt, not from code.

orch new --title "foobar root" --agent orchestrator `
  --skills orch-brief,orch-ask,orch-report `
  --goal "Make three PowerShell scripts in this repository: hello.ps1, add.ps1 and today.ps1. Start one worker child for each script, each with worktree true. Each child commits on its own branch and reports done with the branch name. Review each branch. If the review passes, merge it with: orch merge BRANCH --base main. Then report done." `
  --done-when "main has the three scripts and each one runs."
2
Terminal 1 or the UI, tab Sessions

The root calls spawn_child three times, then ends its turn. Each child gets its own worktree folder next to the repository.

orch tree
1f00aa11 foobar root [supervisor, idle]
  1a2b3c4d hello.ps1 [supervisor, running]
  5e6f7a8b add.ps1 [supervisor, running, 1 open]
  9c0d1e2f today.ps1 [supervisor, running]

The three workers run at the same time. The supervisor runs up to 4 turns at one time. Each worktree is a folder next to the repository, for example ..\foobar.wt\orch-1a2b3c4d on branch orch/session-1a2b3c4d.

3
Nothing to do

Each child reports done. The supervisor sends each report to the root as a message that starts with "Report from child". Each report starts a root turn. The root reads the diff and runs the script, then runs orch merge.

4
The UI, tab Queue

If a child asked a question that got a default, orch merge refuses its branch. The root reports the branch as ready and waits. You review the default in the Queue: Approve, Change or Refuse. After Approve, tell the root to merge again.

orch review toolu_01Cd approve
orch send 1f00 "The default is approved. Merge the branch of add.ps1."
5
Terminal 1

Check main, then archive the children and the root.

git log --oneline --graph
orch archive 1a2b; orch archive 5e6f; orch archive 9c0d; orch archive 1f00
Example 3 From a chat in the Claude Code app

A normal chat session in the app can run orch for you. The chat is the remote control, and the supervisor does the work.

1
A chat in the app

Ask in your own words. The chat runs orch new with a brief, as in example 1 or 2.

You: Start a worker on foobar that makes the three scripts. Tell me when it asks something.
2
The same chat

Ask for the state at any time. The chat runs orch status and orch decisions, and shows each question in the full format. You answer in the chat, and the chat runs orch answer.

You: Status?
You: For add.ps1, use arguments.

The chat does not get a signal when a worker asks. Ask it, or tell it to watch the session in the background.

3
Terminal or chat

Read a supervisor session in the app sidebar. orch open imports the session into the app.

orch open 3f2a

If you type in that session, its hooks take the lease live, and your messages go in directly. The supervisor does not start turns for it until 15 s after you close it.

4
Any app chat, not tested yet

Put your own chat under the orchestrator. Type /orch-enable. The chat gets the mcp__orch__* tools, and inbox messages arrive when it is idle.

All state is in files in store/. No process calls another process through a network API. Each process reads the files, makes its decision and writes new files. Only these process starts occur:

  • The supervisor starts one claude -p process for each turn, and one for each docs check.
  • An agent in a turn runs orch, git and gh through its Bash tool.
  • The hook of spawn_child runs orch new.

The UI, the API and the supervisor are in one process. They share one FileStore object, but they also talk only through the files.

Call stack of one tick

The supervisor does all its work in this loop. Nothing else starts a turn.

TickService.ExecuteAsync                     every 3 s
└─ Supervisor.Tick                          one lock, one pass
   ├─ StopRunningTurns                       control.json stopped → cancel → kill each recorded descendant of claude
   ├─ for each enabled session that is not stopped:
   │  ├─ ReleaseStaleLease                   lease live + heartbeat older than 15 s → lease none
   │  ├─ ForwardReport                       report done/blocked, not forwarded → inbox of the parent
   │  │  └─ store.Send(parent, Texts.ChildReport) + event report.forward
   │  └─ ApplyPolicy
   │     ├─ StartDocsCheck                   level checkDocs → ClaudeDocsChecker in the background
   │     └─ DefaultRule.IsDue → SaveAnswer(by policy) + event answer
   └─ for each session, while running < 4:
      └─ StartTurn
         ├─ Recovery.Interrupted → Recover   turn.json with no ended
         ├─ CanRun                           not running, not live, no cooldown after 3 failures
         ├─ store.Pending                    inbox after cursor + answers not delivered → one prompt
         └─ Track(RunTurn)                    background task
            ├─ Lifecycle.MakeWorktree         first turn with worktree: true
            ├─ Events.Append(turn.start) + write turn.json
            ├─ ClaudeRunner.Run
            │  └─ Claude.Run                  claude -p --output-format stream-json --verbose
            │                                   --setting-sources user --session-id|--resume id --agent orch:<agent>
            │                                   prompt on stdin, ORCH_HOLDER=supervisor
            ├─ ok   → MarkSent (cursor, delivered/) + event turn.end
            ├─ fail → Fail (count, cooldown 5 min doubling) + event turn.fail
            └─ EndMarker                      turn.json gets ended

GroupKindsWriter

The stream is a record. The supervisor does not act on events. It acts on the session files. The Timeline page and orch events read the stream. Refs link the events, for example turnStart on each session.input, and recovery uses this link.

The code moves messages, answers, reports and limits. The prompts and the brief decide the steps of the work: when to split it, when to review it and when to merge it. In example 2 of the tutorial, the brief itself gives the merge command. No file defines a stream as a sequence of steps. This is the gap for the stream definition talk.
