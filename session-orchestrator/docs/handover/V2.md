## Open question: D2 (revised)

**Question:** Which whole system becomes our owned base, and who makes its Blazor layer?

**Words of the user, first (2026-11-24):** "I think we can do our own components, but I feel that we can probably also pick a design system as a base, fully fork it, like it's more than forking, right? Like we can clone it, take out its guidelines, take out its structure, but make it ours. [...] I was trying to do that with WebAwesome, that's open source, fully cloning it, but then, you know, vendoring out everything, so removing all links to the previous one, but we can keep the structure, the documentation, the guidelines. We have even a repo that we started to do that VSA design, we just didn't get to the end, and I started to feel like it was a bit more complicated than we wanted to."

**The goal (2026-11-25; "Web Blossom" is probably a dictation of "Web Awesome"):** "I want to have a design system that has that's already structured, so we can just, own it and customize it [...] Web Blossom already has these guidelines of how to customize things, how to create variants of things, how to create themes and whatnot, right? Most design systems have. And they also are come with plenty of components with, well-structured behavior, button, drop-down, etc. that you can just customize. And not say customize per app, it's like take the whole thing, then, add our twist to it, and then we have our own design system, and then each of our apps customized to their needs, but our base is fully owned by us. [...] we need to create the guidelines so agents know how to work in the future, so they don't slowly break things out and we lose with the design system in just a mess. So the idea was to get one that already has the skills, the guidelines, everything needed. And then we add, for example, the Blazor components that don't have it. We change the nomenclature. We remove links to source things [...] The final expectation is that not only if you ever want to change something, instead of letting an AI agent run crazy, we have either guidelines or tools or skills that know exactly how to change a color, how to add a color, how to change a style, how to add an animation, how to compose something. And eventually be able to even have a declarative way to just, write a JSON. And it renders the screen because everything is a component with guidelines."

**The criteria (2026-11-25):** "We don't really need a design system that has already the JSON component. Like it's an interesting thing, but something we can build on top. The biggest thing is having a structured design system, ideally with skills or MCPs that's easy for us to copy, so that, or at least a very structured guide on how to customize anything, and that has a proper tiered system. Like at least tokens, styles, components, at least that."

| Option | For | Against |
|---|---|---|
| A `vsa-design` (copy of Web Awesome 3.14.0, MIT) | Passes each must; most complete guide; 74 elements; 2 usage skills; most fork steps done | No change skills, no MCP server, Blazor wrappers to make, names still `wa-` (its issue 10), web components conflict with the JavaScript rule |
| B new fork of NVIDIA Elements (Apache-2.0) | Clearest token tiers; authoring skills; local MCP server in the CLI source (`nve mcp`) | The fork work starts again (names, brand, Go and pnpm build); same Blazor wrapper work; same rule conflict |
| C new fork of Blazor Blueprint (Apache-2.0) | Native Razor, mobile parts | One token tier; we write the guides and skills; only Blazor apps; Tailwind styles |

**Recommendation:** A, with B as the model for the change skills (with its Apache-2.0 notice we can copy its skill text). If an MCP server from day one is more important than the fork work, choose B. If web components and Blazor conflict in the spike, choose C. No default.

## Spike: ping pong

Source: `spikes/pingpong/`. Results: tab 7 and `docs/plan.md`, "V2 spike: ping pong". Ports 7931 (engine) and 7932 (web). Data in `%TEMP%\pingpong`. It needs .NET 10, WebView2 and Python on Windows.

```powershell
cd session-orchestrator\spikes\pingpong
foreach ($p in 'Engine','Web','Widget','Notify','App') { dotnet build "PingPong.$p" -c Release }
.\run.ps1                                  # engine, web, widget, notify; -Share uses one browser
python probe.py widget state               # send a command to a head
python probe.py widget exit                # stop one head
Get-Process PingPong.* | Stop-Process      # stop the rest
```

Android (after the toolchain below):

```powershell
$o = "$env:LOCALAPPDATA\orch-android"
$env:DOTNET_ROOT = "$o\dotnet"; $env:DOTNET_CLI_TELEMETRY_OPTOUT = '1'
$env:ANDROID_SDK_ROOT = "$o\android-sdk"; $env:ANDROID_HOME = "$o\android-sdk"; $env:ANDROID_AVD_HOME = "$o\avd"
& "$o\dotnet\dotnet.exe" build PingPong.Android -c Release -f net10.0-android -p:AndroidSdkDirectory="$o\android-sdk" -p:JavaSdkDirectory="$o\jdk" -p:RuntimeIdentifier=android-x64 -p:PublishTrimmed=false -p:RunAOTCompilation=false
Start-Process "$o\android-sdk\emulator\emulator.exe" '-avd orch-phone -no-window -no-audio -no-snapshot-save -no-boot-anim'
$adb = "$o\android-sdk\platform-tools\adb.exe"
& $adb wait-for-device
& $adb install -r (Get-ChildItem PingPong.Android\bin -Recurse -Filter *-Signed.apk | Select-Object -First 1).FullName
& $adb shell am start -a android.intent.action.VIEW -d 'pingpong://hits/3'   # open a page by link
& $adb emu kill                            # stop the emulator
```

- The app connects to the PC on `10.0.2.2:7931`. Start the engine first.
- The project puts its intermediate files in `%TEMP%\ppo`, because a long worktree path stops `aapt2`.
- The Windows projects remove the WPF control of the WebView2 package from the references.
- A lost connection throws a different exception type on Android, so `GameClient` catches all types. Before this, the app did not connect again.
- The first run and the final run gave different checks. Tab 7 says which.
- Memory of 3 heads: 642 MB with separate browsers, 316 MB with one shared browser. One measure each.

To make it again on a new PC (ask first: downloads of several GB). This recipe comes from the install logs, the folder and `spikes/android/README.md`. It was not run again from zero.

```powershell
$o = "$env:LOCALAPPDATA\orch-android"; New-Item -ItemType Directory -Force $o, "$o\avd" | Out-Null
Invoke-WebRequest https://dot.net/v1/dotnet-install.ps1 -OutFile "$o\dotnet-install.ps1"
& "$o\dotnet-install.ps1" -Version 10.0.404 -InstallDir "$o\dotnet"
$env:DOTNET_ROOT = "$o\dotnet"
& "$o\dotnet\dotnet.exe" workload install maui-android
cd session-orchestrator\spikes\android      # installs the JDK and the SDK parts
& "$o\dotnet\dotnet.exe" build -t:InstallAndroidDependencies -f net10.0-android -p:AndroidSdkDirectory="$o\android-sdk" -p:JavaSdkDirectory="$o\jdk" -p:AcceptAndroidSDKLicenses=True
$env:JAVA_HOME = "$o\jdk"; $env:ANDROID_HOME = "$o\android-sdk"; $env:ANDROID_AVD_HOME = "$o\avd"
$bin = "$o\android-sdk\cmdline-tools\19.0\bin"
& "$bin\sdkmanager.bat" --sdk_root="$o\android-sdk" 'emulator' 'system-images;android-35;google_apis;x86_64'
& "$bin\avdmanager.bat" create avd -n orch-phone -k 'system-images;android-35;google_apis;x86_64' -d pixel_7
```

Set `hw.ramSize` to 2G and `hw.cpu.ncore` to 4 in `avd\orch-phone.avd\config.ini`. Windows needs the Windows Hypervisor Platform feature. Use this `dotnet` only for Android: the system `dotnet` has no workloads.
