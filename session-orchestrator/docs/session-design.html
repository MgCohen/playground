Session Registry Design

Each session is one entry in a session registry: an id, a cascading code, a title, its tree, owner, tags, work stream, mode and settings. The registry is a storage port with one writer, apart from the run state (lease, turn, heartbeat). Claude Code is one engine behind an engine adapter, so another engine joins with the same messages.

Design rules

  • Three names for each session: the id finds it, the code places it in the plan, the title tells what it does.
  • The app title starts with the full code, for example [O2 P1 S1], so the user finds the root of each session.
  • One writer for the registry: the registry service. Plugins send a request envelope.
  • Settings are typed fields, not brief text. A mode is a preset of four axes. The brief shows a render of them.
  • Engine first. If the engine gives a function (attach, title, Remote Control, archive, transcript), the adapter uses it. The registry keeps only a reference and adds only what no engine gives.
  • The direction decides. Code that touches a model or a model session (create, talk, change it on the engine side) goes through the adapter. A call into our system (start the tray, write a record, post an envelope) needs no adapter, whoever makes it.
  • One store root. The registry, the run state and the event stream stay together under one root. If the root moves, all of it moves.
  • All engines use the same envelopes. Only the adapter knows the engine.

The registry is one more port

// Orchestrator.Core/Sessions. The file implementation uses IDocStore keys.
public interface ISessionRegistry
{
    SessionEntry Create(NewSession spec);                 // id from the engine, posts session.created
    string FullCode(string id);                           // "O2 P1 S1": codes from the root down
    SessionEntry? Get(string id);
    IReadOnlyList<SessionEntry> List(SessionQuery q);   // parent, tag, stream, owner, phase
    SessionEntry Update(string id, int rev, SessionPatch patch, string by); // refuses an old rev
    SessionEntry? FindByEngineId(string kind, string engineId);
}

public static class StoreBackends   // H1 composition root, one more line
{
    public static Store Create(string root) =>
        new(new FileEventLog(root), new FileDocStore(root), new DocSessionRegistry(new FileDocStore(root)));
}
  • Place: store/sessions/<id>/session.json, beside the run state files. A later implementation can keep the registry in a database and the run state in files.
  • Writer: the registry service in C#, in the supervisor process or in an orch process. Each write takes the lock session.json.lock and checks rev.
  • Plugin: never writes. It posts session.update (the meta.update rule of B2), and the supervisor applies it.
  • History: each write posts session.created or session.changed with the changed fields. The UI subscribes to these.

All session data stays under one store root

<store root>/   ORCH_STORE, else <orch home>/store. H1 chooses the backend.
  version.json, policy.json
  events/<day>/, bodies/<day>/       the event stream (IEventLog)
  sessions/<id>/session.json         the registry entry (ISessionRegistry)
  sessions/<id>/lease.json, …        the run state (IDocStore)
  subscriptions/, nudges/, claims/, supervisor/

Not in the store: engine data. The engine keeps it in its own place.
  ~/.claude/projects/…               Claude Code transcripts
  app state                          sidebar, app parent link, Remote Control
  • StoreBackends.Create(root) makes the three ports from one root. No port has its own place.
  • If H1 moves the store (a database, a cloud host), the registry, the run state and the stream move together.
  • The store keeps only references to engine data: engine.kind, sessionId, appId.

The registry uses the id that Claude Code uses. The id stays modular: the code reads the engine id only from engine.sessionId, and the adapter gives the registry id. So a registry-made id can come later with one change in the adapter.

Visibility public does the import and Remote Control at the earliest point. The app imports only a session with a transcript, so the earliest point is right after the short opening turn (open-in-app), before the brief. Visibility private skips the opening turn, the import and Remote Control: the brief is the first turn.

What Claude Code owns and what the registry owns

Claude Code owns

  • The transcript and the model context
  • The attach: the app parent link and the parent control
  • The app sidebar entry and the shown title
  • The Remote Control connection and its state
  • The app archive
  • The permission mode and the model

The registry owns

  • The id and the session tree across engines
  • Code, title, owner, tags and work stream
  • Mode and settings
  • The phase: active, stopped or archived
  • The map from engine ids to the registry id
DirectionPathContent
Registry to Claude CodeAdapter methodsCreate, attach, open, set, archive
Claude Code to registryAdapter ReadEngine facts, on demand. No copy in the registry
Claude Code to supervisorRun state, app probesLease, heartbeat, archived in the app

The registry never reads a transcript file and never writes an app file. It keeps no copy of an engine fact, so the two cannot disagree. The registry tree is the source of the tree across engines; the app tree shows the Claude Code part when the attach was possible.

Settings are copied from the parent at create

flowchart LR
  SP["Spec of the creator"] --> CR["Create"]
  PA["Parent settings now"] -->|fields not in spec| CR
  PD["policy.json sessionDefaults"] -->|root only| CR
  CR --> E["settings in session.json"]
  PU["Parent or user update"] --> E
  E --> SV["Supervisor"]
  E --> PL["Plugin"]
  E --> BR["Brief render"]
  • The creator can set each setting in the spec of spawn_child.
  • Each setting that the spec does not set is a copy of the value of the parent at that time. A root copies policy.json sessionDefaults.
  • The parent or the user can change a setting of a child at any time: mcp__orch__configure or orch session set. The supervisor applies only an update from the parent or the user.
  • There is no lookup at read time. Each entry holds all its settings, so each reader reads one file.

A tool joins the registry with three commands

# 1. Join: the registry makes the entry and gives the id.
orch session join --engine codex --engine-id 019a-… --parent ca72efff --title "Lint pass"
# 2. Take the lease and keep the heartbeat while the tool runs.
orch lease take <id> --holder live --pid $PID
# 3. Receive and send the same envelopes as a Claude Code session.
orch watch --to session:<id> --render session
orch post question --from session:<id> --body q.json
orch post report   --from session:<id> --body r.json
  • The party is session:<registry id> for each engine. The engine id is only in engine.
  • The templates, the relay, the policy and the inbox do not change.
  • A tool with no lease gets no live delivery. If its adapter has Resume, the supervisor runs turns. Else the input waits and the watchdog posts delivery.blocked.
  • A cloud tool calls the supervisor HTTP API through the tunnel (H1, D1), never the store files.

Non-goals

  • No storage choice. H1 owns it; the registry is a port on the H1 rules.
  • No work stream workflow. C1 owns it; the registry keeps only the key stream.
  • No write to Claude Code files. Reason: internal formats change without notice.
  • No copy of a function that the engine gives. Reason: two copies can disagree, and the engine version gets updates.
  • No list of children in the entry. Reason: a query cannot disagree with the parent field.
