Tray Test Guide

How the tests of the tray work: what a check is, how the data flows, and where the agent decides. Each tab has one topic. Start with the overview.

Four test runs, one app

All runs start the real tray app (Orchestrator.Tray) with a flag. The app drives itself, then writes files. Nothing is a mock.

What is a check?

A check is one line in SelfTest.cs: a name, a pass rule and a message with the measured values.

Add("sheet-in-panel",                       // name
    Ints(scrim).All(v => v == 0),               // pass rule: all differences are 0
    $"scrim minus panel [left, top, width, height] = {scrim}");  // message: the data

The result goes to selftest.json and to the console as PASS or FAIL.

The checks prove facts that have a number: a size, a place, a phase, an alpha value, a frame count. They do not prove that a motion looks correct. That part is a human or agent review of pictures and video.

An empty frame is a frame in which the tray is not on the screen, but the frames before and after show it. The recorder sees what Windows really shows. The self-test picture (CapturePreviewAsync) does not see empty frames, because it asks the page for a new picture.

Worked example: does a tab click put the nav dot under the tab?

Spec T1: one nav dot moves under the current tab with a spring, and it hides on Home. Open each step.

Write the rule as numbers agent
  • On a tab: the dot center minus the tab center = 0 px, and opacity 1.
  • On Home: opacity 0.
Do the click automated
await Js(w, $"{Go}('{item}')");   // the router opens the tab, as a user click does
await Task.Delay(700);            // the spring ends
Measure in the page automated
const d = nav.querySelector('.ndot'), on = nav.querySelector('.it.on');
return { off: d.classList.contains('off'),
         opacity: +getComputedStyle(d).opacity,
         dx: Math.round(dotCenter - tabCenter) };
Pass or fail automated
PASS dot-cards: dot {"off":false,"opacity":1,"dx":0}
PASS dot-home:  dot {"off":true,"opacity":0,"dx":null}
What it does not prove you

The end state is correct. The spring path between the two places is not measured. A video shows it.

Make a hypothesis and test it agent

The agent picks one cause and turns it off with one CSS rule. Then it runs the same stress.

--css ".scrim { animation: none !important; }"
result: about 1 empty frame in 60 s, not 5 to 6

The agent read this as "the scrim fade is the cause". That was wrong: see the next step.

Look at the frames agent you

A strip of the five frames around each empty frame shows what the number means. Here the strips showed the tray in each "empty" frame. The scrim fade moved the frame mean through the backdrop mean. The detector was wrong, not the tray.

Lesson: look at the frames before you test causes. The issue tracker (I1, I2) has the strips.

Add a check

  1. Open src/Orchestrator.Tray/SelfTest.cs, method Run.
  2. Do the action: w.Request(...) for the window, Js(w, $"{Go}('path')") for a page.
  3. Wait for a state with Until(...), not only with a delay.
  4. Measure with Js, the window fields or Picture.
  5. Call Add(name, rule, data). Put the measured values in the message.
// Template
await Js(w, $"{Go}('cards')");
await Until(async () => await Js(w, "!!document.querySelector('.x')") == "true", 3000);
var v = await Js(w, "Math.round(document.querySelector('.x').getBoundingClientRect().width)");
Add("x-width", v == "280", $"width {v} (expect 280)");

A new check must fail first. Revert the fix, run the check, see FAIL, then restore the fix and see PASS.
