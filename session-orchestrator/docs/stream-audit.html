Stream Audit

Does each feature read from and write to the event stream, or does it bypass it? This page holds the context, the rules of the audit, the open questions and the plan. When the user agrees the rules, the audit result goes on a fifth tab.

Draft Rules proposed, not agreed. Branch orch/d-data-upgrade.

The stream is the pillar

The store contract (docs/store.md) says that all communication goes through one event stream. A sender posts a body and an envelope. Each party gets a push, then queries and reads what it needs. The target app is reactive: pages only read the stream, and actions only write to it.

Why an audit

A session can understand an idea and build it wrong. Example: the provider rule asked for one IProvider, and a session made one adapter for each feature. The same risk applies to the stream. A feature can post envelopes and still keep its own files or its own state.

First signals

These are signals from a first read. They are not audit findings yet.

  • StateReader.Read builds the session snapshot from status.json, lease.json, heartbeat.txt, turn.json and the envelopes together.
  • LiveView loads the full page again on each file change, and also on a 10 s timer.
  • LiveView.Act runs the action, then calls Load() at once. It does not wait for the envelope.
  • Board is one large read model for all pages. It calls FileStore, the lifecycle and the inbox directly.
  • TickService runs the supervisor tick on each push and at least each 5 s for the time rules.

Target topology: one loop

Each action posts. The stream pushes. Each view folds the stream into a projection and shows it. No arrow goes from an action to a view.

Rules

#RuleCheck
R1Each domain fact is an envelopeNo fact lives only in a file
R2A view reads only projections of the streamNo view reads a side file
R3An action only postsNo action writes a file or a field
R4A projection is a cacheDelete it, rebuild it, same result

A bypass is a domain fact outside the stream, a view that reads a side file, an action that writes a side file, or a projection that the stream cannot rebuild.

Example: bad and good

Bypass 
// Plugin: the turn state goes to a file.
await writeSession($, 'status.json',
  { state: 'running', turnId, at })

// Page: the view reads the file
// and polls each 10 s.
var status = store.Status(id);
timer = new Timer(_ => Reload(), …);

The fact "turn started" is only in a file. No other party sees the change as a push. A rebuild of the stream does not give the state back.

Through the stream 
// Plugin: post the fact.
await post($, { kind: 'turn.start',
  from: self, to: 'supervisor', turnId })

// Projection: fold the envelopes.
SessionState Fold(SessionState s, Event e) =>
  e.Kind switch {
    "turn.start" => s with { Running = true },
    "turn.end"   => s with { Running = false },
    _ => s };

// Page: render on each push.
Hub.Changed += () => Render(projection.Of(id));

The fact is an envelope. Each party sees it. The view state is a fold that a replay can rebuild.

Q1. How strict is the rule for session state?

Context
A3-2 kept status.json, lease.json, heartbeat.txt and stack/ as files: "Stream B owns them". A strict rule makes each of them a bypass.
Options
(a) Strict: all state is a projection; files are caches only. (b) Messages only: lifecycle files are allowed. (c) Mixed: lifecycle facts are envelopes; plumbing stays in files.
Recommend
(c). Cursors, claims and nudges are mechanics of the stream. A turn start or a lease change is a fact that a page shows.

Q2. Is a poll timer a bypass? Default: (a) yes

Context
LiveView reloads on a push and also each 10 s. TickService runs at least each 5 s.
Options
(a) Yes: a data poll is a bypass. (b) No: the audit checks only the data source.
Recommend
(a). A poll hides a fact that has no envelope.

Q3. Are time rules events?

Context
Default timeouts, reminders, the watchdog and the stale lease depend on the clock, not on an envelope.
Options
(a) The supervisor posts a timer event (for example default.due) when a time passes. (b) A sweep over the projection is allowed for time only.
Recommend
(b) for the audit, with one rule: the sweep reads only projections and writes only envelopes.

Q4. How deep is the audit? Default: (b) full depth

Context
The brief names the Web pages, the store and the plugin hooks.
Options
(a) Web, Store, Supervisor and the hooks. (b) Also the CLI, the tray and the providers.
Recommend
(b). The CLI and the tray also write state.

Q5. Do you know a bypass to examine first? Default: (b) start from the code

Context
A known example helps to calibrate the audit, as the provider case did.
Options
(a) Yes: name it. (b) No: start from the code.
Recommend
(a), if you have one.

Q6. Is config a domain fact?

Context
policy.json and templates/ change the behavior of all parts. A running supervisor reads templates only at start.
Options
(a) Config changes are envelopes (for example policy.change). (b) Config stays in files, outside the audit.
Recommend
(b) for this audit. Record a note for session K.

How to trace a feature

  1. Start at the entry point: a page, a button, a CLI command, a hook or a tick step.
  2. Follow each read to its source. Note each call to IRepositories other than Events and Bodies.
  3. Follow each write to its target. Note each WriteJson, Put and writeSession.
  4. Find the update trigger: a push, a timer or a direct reload.
  5. Ask: if the stream is replayed into an empty store, does this feature show the same state?

Order of the fix tasks

  1. Facts first: post an envelope for each fact that lives only in a file. Keep the file as a cache.
  2. Projections next: fold the envelopes into one projection for each view. Add a rebuild test.
  3. Views last: move each page to its projection. Remove the poll timers and the side file reads.
  4. Clean up: remove the side files that no reader uses. Change docs/store.md in the same commit.

This order keeps the app working after each task.
