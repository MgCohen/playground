session-orchestrator · B1 design

Session Lifecycle

Each session has one lifecycle state. The supervisor calculates it at each tick (3 s) from the store files, in a fixed order, and writes an event when it changes. Each state has one detector, one action and the messages that the change needs. Stream A designs the message formats.

Nine states, one main path

The main path is start, running, idle, done, archived. The warning states (orange border) show a session that needs help. A user or a parent can stop or archive a session from each state.

Order of the checks

More than one signal can be true at the same time. The supervisor uses the first state that matches, in this order. A stop is stronger than a fault, and a fault is stronger than a turn.

OrderStateMatch
1archivedcontrol.json archived, or no enabled file
2stoppedcontrol.json stopped
3staleLease live and heartbeat older than 15 s
4not respondingOne of the four faults (States tab)
5startNo good first turn yet
6runningSupervisor turn, or status.json running
7doneLast report done, no input after it
8forgottenIdle 15 min, no final report, no wait
9idleAll other cases

An idle session can wait for something. The state stays idle, and a wait reason shows why: an open decision, an open child, or a blocked report.

State details

One foldable for each state. Each foldable gives the entry, the exit, the behavior in the desktop app and the edge cases.

start · new session, no good first turn
Enter
spawn_child, orch new or POST /api/sessions writes meta.json and enabled.
Detect
createdBy is set and started is not true.
Action
The supervisor makes the worktree and runs claude -p --session-id with the brief. After the first good turn, it imports the session into the app and turns Remote Control on, unless the brief says background: true (F4).
Exit
A good turn goes to running, then idle. Three failed turns go to not responding.
In the app
orch enable in an app session skips this state. It writes started: true, so the session is running at once.
running · a turn is in flight
Detect
Holder supervisor: the supervisor has a running turn, and turn.json has no ended. Holder live: status.json is running and the heartbeat is fresh.
Action
None. New inbox files wait. update calls go to the user only.
Exit
The turn ends: idle, or done if the turn sent a done report.
Edge case
A turn that writes no event for 30 min counts as hung: not responding.
idle · no turn, possibly a wait reason
Detect
No running turn and no input that waits for delivery.
Wait reason
decision (an open decision), child (a child that is not done), blocked (the last report is blocked), or none.
Action
If an inbox file or an answer arrives, deliver it. Holder live: the plugin submits it. Holder none: the supervisor runs claude -p --resume.
In the app
An idle app process ends after about 3 h 45 min (S11). session.end sets the lease to none. This is a normal idle session, not a stale one.
stale · lease live, heartbeat old
Detect
Lease live and heartbeat.txt older than 15 s, with no session.end. Causes: the app crashed, the computer slept, or the plugin is not active (W1).
Action
The plugin writes its process id and start time in lease.json. If that process is gone, the supervisor releases the lease to none, and the session is idle. If the process is alive for 2 min with no beat, the session is not responding. The supervisor does not resume it.
Reason
A claude -p turn next to a live app process makes two writers (S0). The process check prevents this.
Exit
A new beat: back to the state before. Process gone: idle.
not responding · four faults
FaultSignalAction
Failed turns3 failures, then backoff 5, 10, 20 minTry again after the backoff
Stop latchblocked.json reason from the pluginTell the user to type in the session
Input not takenLease live, idle, inbox older than 2 minTell the parent, keep the inbox
Hung turn or processNo event for 30 min, or stale process aliveTell the parent; the user stops it

The parent gets one notice when the state starts and one when it ends. The supervisor never uses a peer message to go around the Stop latch.

forgotten · idle with no final report
Detect
Idle for 15 min, last report not done or blocked, no wait reason, no input after the last turn.
Action
Send one nudge to the session: report done or blocked, or continue. If the session is still forgotten 15 min after the nudge, tell the parent.
Exit
The nudge starts a turn: running.
Edge case
A root session has no parent. The notice goes to the user queue.
done · final report
Detect
The last report has state done, and no input arrived after it.
Action
At the end of the turn, the supervisor sends the last report to the parent. Two reports in one turn give one notice (F5). The parent archives the child when it has no open PR.
Exit
A review or a message starts a new turn: running. orch archive: archived.
Edge case
A done child with no open PR that is not archived after 1 h gets one reminder to the parent.
stopped · the user or the parent stopped it
Enter
orch stop, the API or the UI writes control.json with stopped.
Action
The supervisor ends the running turn and kills each recorded descendant (D2). It starts no turn. The plugin of a live session also reads control.json and submits no inbox file.
Exit
orch resume: idle. The inbox goes at the next tick.
archived · end state
Enter
orch archive. It refuses open decisions and open PRs without --force.
Action
Archive in the app first (F8), then the store side: control.json, delete enabled, remove a clean worktree, keep the branch. The plugin sees no enabled and releases the lease.
Edge case
The user archives a session in the app sidebar. session.end fires, and the app record shows isArchived. The supervisor asks the parent or the user to archive the store side too.

F4: Remote Control on by default

Each session has Remote Control on, also a child. A session has it off only when its brief says background: true. This rule replaces the F15 rule "root only". claude --desktop --resume --remote-control does not import (F4), so the start does not use a CLI flag.

flowchart TD
  A[First good turn] --> B[Import into the app]
  B --> C{background: true?}
  C -->|yes| D[Remote Control stays off]
  C -->|no| E[remote-control-self notice]
  E --> F[Session calls set_remote_control on itself]
  F -->|refused| G[Parent calls it with child appId]
  • The self call uses the same method as archive-self (F14): an inbox notice, and the session calls the app tool with self.
  • meta.json records remoteControl: true or false. The archive reads it.
  • An archive needs Remote Control off first (F9). enabled: false shows an app prompt (F15). With Remote Control on by default, each archive of a child can show this prompt.

F5: a step report is an update

  1. The supervisor forwards a report only when the turn ends. If one turn sends two reports, the parent gets the last one.
  2. The report tool refuses done while the session has an open decision. Its result tells the model to call update.
  3. The skill orch-report and the agent worker say: the end of a step is an update.

F8: archive in the app sidebar

flowchart TD
  A{Live in the app?} -->|yes| B[archive-self notice]
  A -->|no| C{Parent live in app?}
  C -->|yes| D[Parent calls archive_session]
  C -->|no| E[User archives from sidebar]
  B --> F[Store side archive]
  D --> F
  E --> F

Path 2 needs a probe: can an app session archive another session by its app id? Remote Control must be off before each path (F9). The store side always runs, so the supervisor never runs the session again.

Delete of mod/orch/

The B1 branch deletes mod/orch/. No session loads it: CLAUDE_CODE_PLUGIN_DIRS points to plugin/, and no code refers to the folder. The user approved the delete before the next app restart. mod/orch-spike/ stays as a spike record.

Non-goals

  • No message formats in B1 or B2. Reason: stream A owns them.
  • No UI change. Reason: the UI reads the API field in a later step.
  • No automatic archive. Reason: the parent or the user decides, and open PRs need a person.
