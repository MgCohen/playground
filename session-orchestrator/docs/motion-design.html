S1

Page actions

The Document page is one page for many types: a question, a plan, a report, a review. Change the page in the sample and tap the corner button.

  • Page actions belong to the page, not to its content: Open session and Archive are on each Document page. They are in a bar at the bottom of the screen, always in the same place. The page content scrolls above the bar and never goes under it.
  • Content actions change with the content: Accept for a question, Approve for a plan. They are in the corner button, which floats above the page bar. A tap opens them as a speed dial. The main action is first. Danger actions are last, in red.
  • The corner button shows only when the content has actions. Any page can use it, so it is the one place for content actions. Session status has only page actions, so it has no corner button.
  • App bar: each page sets if it shows the app bar. A page that needs the full height hides it. The header path is the way back.
APage bar + corner buttonYour design: page actions in a fixed bar at the bottom, content actions in a corner speed dial above it. Pick the app bar rule in the sample.

Build: a page gives two lists, each action with a role: page actions and content actions. A shared page bar shows the first list. A shared corner button shows the second. A layout flag on the page hides the app bar. The content actions can later come from the document type.

T3

Header path

The header keeps the path of the sub-pages: Sessions › orch-bad3 › Stream › Question. Tap a row to go deeper. Tap a part of the path to go back to it. A tab in the app bar starts a new path, because tabs are on the same level.

AFull pathThe parents are small links with "›" between them. The current page is the last part, in the same font, bold and darker. If the path has more than 3 parts, the first parts become "…", so the last two parents always show in full. A tap on "…" goes to the hidden part.
BBack + titleOnly the parent shows, as "‹ Parent", then the title. Short, but you see only one level.
CTwo linesThe path is a small line above the title. The full path has more space, but the header is taller.

Build: a small path service in Blazor. Each sub-page adds its part, and a tab change clears the path. The header moves into the shared layout. The path motion uses the same View Transition as T2.

G1 · load

Open before the page is ready

If the page is ready, the widget only grows. If not, the home button floats and pulses, then the widget grows behind it. The content fades in when it is ready, but never during the grow.

While it loads
RRevealThe page stays still. The top edge goes up and shows more of it. This is the build now.
+Reveal + rise or fadeReveal, and the page also rises 40 px or fades in. Softer.
ZResize or stretchResize changes the real height, so the page lays out again on each frame. Stretch squashes the page. Both cost more in the app.

Build cost in the app. The Windows shadow cannot fade: it is on or off. "Fade in after" and "Grow with" need a second, see-through window behind the widget that draws the shadow. The floating button is a small native window too, because the page is not there yet. The skeleton and the content fade are CSS in the page.
