Review

The findings about the part, good and bad. One item for each finding.

Card types are dataGoodUi.Classify gives each card 1 of 8 types, with 2 actions

Ui.Classify makes a CardView with its type, group, label and 2 CardAction values. The deck, the home ring and the badge counts read it. The test Each_card_type_has_its_own_actions checks 6 of the 8 types.

Page depth is an attributeGood[PageDepth] on 3 pages; PageDepth.Move picks the move

PageDepth.Move reads the routes and the [PageDepth] attribute of each page. MotionHost and MainLayout use it. The tests The_move_comes_from_the_depth_of_the_two_pages (9 cases) and A_page_gives_its_depth_with_the_attribute check it.

Each motion step is one registry rowGood11 rows; tests compare rows, targets and CSS rules

MotionSteps.All has 11 rows. Registry_matches_motion_css compares the rows, the data-motion elements and the step rules in both directions. Each_state_class_has_a_rule checks each state class.

The page owns each tray sizeGoodR2: tray.css tokens, orchTray.sizes reports them

The windows keep no size constant, only TrayWindow.Gap. The tests Tray_window_sizes_come_from_the_page and Tray_sizes_are_tokens check it. In the trace, the panel window is 597 × 1152 at 1.5 DPI: (350 + 2 × 24) × 1.5 and (720 + 2 × 24) × 1.5.

Each look has one componentGoodthe name of the look gives the Razor component

LookComponents maps each look name to the component <Name>Look. The test Each_look_of_the_catalog_has_one_app_component_and_one_page_function compares the catalog, the components and the design page.

Small pure rule unitsGoodTrayCounts and TrayNotices have no I/O; TrayNoticeTests

TrayCounts.Of (TrayCounts.cs:11-15) and TrayNotices.Take (TrayNotices.cs:15-21) read only their arguments. TrayNoticeTests tests the notice rule directly, with no page.

G1 · The size report has no sourceGapWidgetWindow picks the window from the shape of the report

WidgetWindow.UseSizes sends a report with no Rest box to the panel window, and the others to the badge window (WidgetWindow.cs:115-116). orchTray.sizes gives no boxes when .tb-tab has no box. If the badge page gets a phase with display: none, its report goes to the panel window.

To close it: let each root give its report to its own window, for example IWidgetWindow.UseSizes(source, sizes).

G2 · The test slot width is a C# constantGapSlot.Width = 460 has no link to the tray tokens (P-D3)

Slot.Width in Slot.cs is 460. No code links it to --tray-panel-w, --tray-margin and TrayWindow.Gap. A wider panel token can make two test trays overlap. It touches the test tools only.

To close it: a test reads the tokens of tray.css and asserts that Slot.Width is at least the panel width + 2 × margin + Gap.

G3 · The card type is a free stringGap8 values; 3 places compare the text, no compile check

CardView.Type is a string. CardView.SheetLabel, CardView.SendLabel (Ui.cs:45-57) and Board.SendSheet (Board.cs:179) compare it with literals. SendSheet checks only "review", so the text of a "plan" card goes to Refuse as a refuse verdict (Inbox.cs:66-67), but the sheet of that card says "Send change".

To close it: an enum for the card type, and one property of CardView for the send path.

G4 · The self-test copies the window step namesGapSelfTest.cs:404 has its own list of the 4 names

The check window-steps uses a literal array of the 4 step names. WindowSteps.All is the source of these names. A new window step does not get a check.

To close it: read the names from WindowSteps.All.

G5 · Two sources for the look of a kindGapview.json, and the C# table Ui.Look as a fallback

Board.Look reads view.json and uses Ui.Look only for a kind with no view.json (Board.cs:153-158). Ui.Look has arms for 9 kinds that have a view.json (Ui.cs:110-119). These arms do not run while the templates exist, and no test compares the two sources.

To close it: keep the C# table only for the kinds with no view.json (blocked, delivery.blocked, turn.fail, pr.*, branch.*, merge.*). Add a test that no kind of the table has a view.json.

G6 · The card group count is in 3 placesGapHomePage, Cards and TrayCounts count the groups again

HomePage.razor:94-100, Cards.razor:117-123 and :147-153, and TrayCounts.cs:11-15 count CardGroup values. The Cards chip "Reports" adds Blocked. The home ring and the badge count Blocked apart.

To close it: one count rule, for example TrayCounts.Of, and one chip rule. HomePage and Cards use it.

G7 · Filter orders are free stringsGapViewFilter.Orders and StreamPage.Orders; 2 pages compare text

ViewFilter.Orders has "Arrival", "Newest", "Session", "Default time" (ViewFilter.cs:8). StreamPage has its own ["Newest", "Oldest"] (StreamPage.razor:45) and compares "Oldest" (:83). Cards compares the names (Cards.razor:155-160). A wrong name gives the default order, not a build error.

To close it: an enum or constants on ViewFilter for each order.

G8 · One name, three looksGapUi.Look(kind), Ui.Look(SessionNode) and Board.Look

Ui.Look(kind, state) gives an icon and a color (Ui.cs:108). Ui.Look(SessionNode) gives a label, a color and a progress (Ui.cs:169). Board.Look(kind, state) gives the icon and color from view.json (Board.cs:153). A caller of Ui.Look can skip view.json by mistake.

To close it: give each one its own name, for example KindLook and SessionLook.

I19 · No "page ready" value in TrayPhaseDependencyowned by Start and stop

TrayPhase has 6 values and no "ready" value. The end of the grow is a private bool of TrayStage (the class is-ready). A test that reads Phase sees open before the grow ends.

Phases are strings and CSS classesTrade-offone name in C#, CSS and the trace; no compile check

Gain: one name for each phase: the C# constant, the class "is-" + phase and the trace line.

Cost: a wrong name gives a missing class, not a build error. The tests check only the phases that are motion states: is-start and is-hidden have no check.

Motion times are read at run timeTrade-offone owner (motion.css); a JS call for each read

Gain: motion.css is the one owner of each time. C# reads it with MotionTimes.Of. A failed read gives null, never 0 s (MotionTimes.cs:16).

Cost: each read is a JS call, and each caller must handle null. Cards.razor:208-214 runs the act with no undo and writes a trace warning.

Ui is one static class for the fixed view factsTrade-offcard rules, looks, time, text and icons in Ui.cs

Gain: one place to look, and no service to inject.

Cost: 169 lines with 5 topics in Ui.cs:61-229: card rules (Classify), looks, time format (Ago, Clock), text coercion (Text, List) and SVG icons (Icons). The card rules are domain rules, and the icons are style data.

Architecture

How the part works: the view of a caller (Outside), and the work after the call (Inside). The Outside graph is a topology: each data source and its readers. The Inside graph is a sequence, because the size report crosses from C# to the WebView2 process and back.

Architecture: mixed. The fixed facts have one clear way: a registry or an attribute, one owner, and a test that compares the source with its users. The view model has no single way: 2 sources for the look of a kind (G5), 3 copies of the group count (G6), and free strings for types and orders (G3, G7).

public static string? Move(string from, string to)
{
    if (string.Equals(from.Split('#')[0], to.Split('#')[0], StringComparison.OrdinalIgnoreCase)) return null;
    // ← an address with no page gives no move
    if (Of(from) is not { } a || Of(to) is not { } b) return null;
    if (a == 0 && b == 0) return Tab;
    // ← the same depth below the tabs gives no move
    return b > a ? Push : b < a ? Back : null;
}

API

The main entry points of the part: the methods, types and messages that a caller uses. One item for each.

classLiveViewa page that loads again at each store change

Requirements

What the part must do. One item for each requirement, with its status and its design.

S-R1 · One set of views for both hostsCoveredRoutes in App.razor and TrayRoot; self-test and bUnit tests

The web server and the tray show the same pages, layout and components.

Design: App.razor and TrayRoot render Routes. The bUnit tests (for example InboxUiTests) render the components, and the tray self-test runs them in the tray.

S-R2 · One path from C# to JSCoveredJsCommand; tests No_direct_js_calls, Js_names_exist

A view does not ask which host it is in, except through the window contract.

S-R4 · The logic outside markup is in slicesPartlyFeatures/, Plugins/ only (G3)

Each unit that is not markup is in a feature slice.

Design: the Umpire VSA check after each build. The test R1_folders_have_no_findings.

Not covered: Components/, Board.cs and Ui.cs (G3).

S-R5 · A hidden view does no workNot coveredLiveView loads in all phases (G1)

While the tray is hidden or at the badge, the panel views do not load.

Design: none in the code. The plan: a check of the phase in LiveView.Reload, and a count of loads while hidden (G1).

Design: none in the code. The plan: one registration method in Orchestrator.Web (G2).

API

methodUseSizes(sizes)IWidgetWindow: give the measured sizes to a window
  • sizes: a TraySizesResult from TraySizes.
  • With Rest null it goes to the panel window, else to the badge window.
  • A visible window takes the new bounds and the new click area at once. A hidden window keeps the sizes for its next show.
commandTraySizes()measure the tray sizes in the page → TraySizesResult
  • A JsCommand: it runs orchTray.sizes through the JS pipeline.
  • It waits for the fonts, so a text box has its final size.
  • Send it with Must: an error throws.
recordTraySizesResult(PanelWidth, …, Bubble)the sizes in CSS px; boxes are [left, top, right, bottom]
  • PanelWidth, PanelHeight, Margin, Tab, TabTop: the tokens.
  • Width: the page width. The badge boxes count from its right edge.
  • Rest, Hover, Bubble: the shadow boxes, or null on the panel page.
methodPeek(on)IWidgetWindow: the click area takes the bubble in or out
  • on: true when the bubble shows, false after the wait peek-out.
  • Report the sizes before Peek(true), so the bubble box has its text.
eventBadgeHovered, BadgeFolded()IWidgetWindow: the hover from the window, the fold end from the page
  • BadgeHovered(bool): the window says that the hover starts or ends.
  • BadgeFolded(): the page says that the step badge-fold ended. The click area gets small if no new hover started.
methodShowAtPlace()TrayWindow, BadgeWindow: show at the place, with the click area
  • Called by WidgetWindow.Enter for the phases start and badge-out, and after a display or DPI change.
  • With no size report it writes a fault and the window stays hidden.
methodUsePlace(point)TrayWindow: set and save the panel place with no drag
  • point: the top-left corner of the panel, in screen pixels.
  • The self-test uses it. The next show clamps it to the work area.

API

methodRequest(what)TrayFlow: ask for open, dock or hide
  • what: TrayRequest.Open, Dock or Hide. Another word does nothing.
  • During a run the request waits, and the task ends at once. Only the last waiting request runs.
  • A caller in a window sends it through the Requested event of IWidgetWindow.
methodBringBadge()TrayFlow: a notice brings the badge in → bool
  • From the phase hidden, the badge comes in.
  • During a run it waits for the end of the run.
  • The result is true when the phase is badge after the call.
methodPhase, ClosedTrayFlow: the phase, and "closed for the user"
  • Phase: a TrayPhase value. It changes after each window step.
  • Closed: true when hidden or at the badge, or when a hide or a dock runs. A running open counts as open.
methodAttach(IPanel), Attach(IBadge)TrayFlow: a page gives its motion steps
  • IPanel: Prepare, Grow, Fold. TrayStage attaches in OnInitialized.
  • IBadge: In, Out. BadgeRoot attaches in OnInitialized.
  • A run waits until the page of each step is attached.
methodEnter(phase), LastEventIWidgetWindow: show or hide the window of a phase
  • phase: a TrayPhase value. Start, open, badge-out and hidden change the windows.
  • The task ends after the change on the UI thread.
  • LastEvent: "shown", "hidden", "activated", or the same word with "not".
classTrayRequest, TrayPhasethe request words and the phase words
  • TrayRequest: open, dock, hide.

API

The main entry points of the part: the methods, types and messages that a caller uses. One item for each.

attribute[PageDepth(depth)]give a page its depth; Query and QueryDepth
  • depth: 0 for a tab page (the default with no attribute). A bigger number is deeper.
  • Query: a query key that gives the page another depth, for example "session".
  • QueryDepth: the depth when the address has the key, for example 1.5.
methodPageDepth.Move(from, to)the move between two base-relative addresses
  • from, to: addresses such as "events/e1" or "stream?session=s1".
  • The result: PageDepth.Tab, Push, Back, or null for no move.
methodPageDepth.Of(relative)the depth of one address, or null for no page

The first route with the same parts gives the depth. A route part in braces matches each value.

commandMotionBegin(Kind)start a view transition: "push" or "back"

Sent only by MotionHost. It returns when the browser has the picture of the old page. It gives no end (Motion G2).

recordMotionSteps.TabInthe step of a tab change: tab-in, is-tab-in

The state class is-tab-in on main.page. The step rule waits for m-rise. Its name is the Key of the wait.

API

recordMotionStep(Name, States)one step of the registry: name, state classes, target
  • Name: the step name. It is the data-motion value.
  • States: the state classes that start the motion. State is the first one.
  • Target: the selector [data-motion~="Name"].
commandMotionWait(Target, Mode, Arg)wait for the end of a motion → WaitResult
  • Target: an ElementReference or a selector. Not used for Frames.
  • Mode: Step (the CSS rule names the wait), Property, Settle, Frames.
  • Arg: for Property the property or animation names ("clip-path scale"); for Frames the number of frames.
  • Key (init): a newer call with the same key cancels the older one.
recordWaitResult(By, Ms)how the wait ended, and its time
  • end: the motions ended. cancel: the browser stopped a motion. hidden: the page is hidden.
  • limit, none, missing: AtLimit is true, and the trace gets a warning.
  • Ms: the time of the wait.
methodSendAsync(command, ct)ICommandSender: send a command, get a Result

Gives a Result<T>. An error is in the result, and the trace has it. Use it in components.

methodMust(command)FlowCommands: send; an error throws a flow fault

For a flow step (the tray stage, the badge). An error throws, and TrayFlow writes a fault. A cancel does not throw.

commandMotionBegin(Kind)start a view transition: "push" or "back"

Sent by MotionHost. It returns when the browser has the picture of the old page, not at the end (G2).

commandMotionDot(Nav)move the nav dot to the current tab

Sent by AppBar. No wait.

commandMotionMs(Token)the value of a token in ms

Used through MotionTimes.Of, for example --t-undo and --t-peek-show.

Review

The findings about the part, good and bad. One item for each finding.

One trace line for each JS commandGooda pipeline step: no caller writes the JS line

JsTraceStart and JsTraceEnd are registered one time in the JS pipeline (Plugins/Js/JsPlugin.cs:21-22). JsTraceEnd writes one line after each JS command, with the call id #n and the time. A JS error is a WARN line; a cancel by a newer call is not (JsTraceEnd.cs:20).

The tests use the real compositionGoodJsPipelineTests: OrchHost.Add and a fake IJSRuntime

JsPipelineTests build the services with OrchHost.Add (tests/Orchestrator.Tests/JsPipelineTests.cs:38), so the test runs the same steps as the hosts. A_JS_error_is_an_Error_with_the_JS_name_and_a_trace_line and A_wait_at_its_limit_writes_a_trace_line check the lines.

Window steps are in the same traceGoodR1 S9: event, time and window gap

TrayFlow.Window writes each window step to IJsTrace: the window event, its time and the gap from the last page step. A wrong event is a WARN line. The test TrayFlowTests.Open_from_badge_order checks the lines.

Each test run has a run recordGoodone JSON file: kind, code, build, time, result

RunRecord.Write writes one new file for each self-test run. The I19 run gave "kind":"stress","code":"I19","build":"e180a34","result":1. ConsoleCopy also keeps the console output in console.txt.

T-G1 · No common format and no common idGap5 writers, 6 files, free text

Each writer has its own text format: Faults, JsTrace, the press log, the phase poll and RunRecord. A press, a JS call and a window step have no shared id. The format is a hidden contract: the checks find lines with Contains("by end") and Contains(" window ") (Orchestrator.Tray/SelfTest.cs:401-405). A change of a format string breaks a check, and no compile error shows it.

To close it: one trace event with fields (time, source, kind, id, result) in one file for each run, and checks that read fields (P-T1, P-T2).

T-G2 · The page writes no trace of inputGapno click, key, swipe or navigation line (I19)

A press in stress.txt says clicked (window messages): the messages were posted, not that the page got them. The page writes no line for a click, a navigation or a swipe. For I19, the trace cannot show where the first presses went.

To close it: the page confirms each input with its element and the page path before and after (P-T3).

T-G3 · The full trace is on only with --demoGapor with a named instance; a plain self-test writes no steps

Faults.Tracing is true only for a named instance with no self-test, or with --demo (Program.cs:74). The I19 run needed --demo to get the trace. A scenario copies only the IJsTrace lines, not the window lines of Faults.Trace.

To close it: each self-test run writes the full trace (P-T4).

T-G4 · Two time stamps on each JS lineGapJsTrace and Faults.Trace both add the time

JsTrace.Add puts the time on the line, and Faults.Trace adds the time again. A line of exceptions.log is 13:39:59.131 [2] 13:39:59.130 js orchMotion.wait(…). The scenario cuts the first 13 characters (line[13..]) to remove one.

To close it: Written gives the line and its time as two values.

T-G5 · The phase is a poll, not an eventGapSelfTest.Phases reads the phase each 10 ms

The scenario finds a phase change with a poll each 10 ms. A change shorter than 10 ms is not in scenario.txt. WidgetWindow.Enter already writes tray phase … (from …), but only when Tracing is on.

To close it: the flow writes each phase change as an event in the trace (P-T4).

T-G6 · The web host shows no traceGapJsTrace logs at Debug; the default level is Information

JsTrace writes to ILogger at Debug, and Warn at Warning. The web host has no log setting, so only the warnings show. The web pages in a browser have no trace file.

To close it: a trace file or an endpoint for the web host, with the same event as the tray.

T-G7 · The file write runs on the UI threadGapinside the motion that the trace measures

Written runs on the caller thread, outside the lock (Plugins/Js/Infrastructure/JsTrace.cs:42). Faults.Trace calls Directory.CreateDirectory and File.AppendAllText for each line, inside a lock (Orchestrator.Tray/Faults.cs:28-33). The window lines and the JS lines show thread [2], the WinForms UI thread. The trace can add time to the steps that it measures.

To close it: put the lines in a queue, and write the file from one background writer.

The window classes call Faults.Trace directly (Orchestrator.Tray/WidgetWindow.cs:70, ClearHost.cs:123, TrayWindow.cs:82). Only IJsTrace lines go to the file through TrayApp.cs:30 and reach Lines. A window event line is not in Lines, so no self-test check can read it.

How the part works: the view of a caller (Outside), and the work after the call (Inside). Each view has one graph and one text call tree. Pick the graph type that matches the concept: a sequence for calls and waits across runtimes, a topology for units and links, a flow for decisions and states.

Mixed. The JS trace has one clear design: a Before step and an After step of the pipeline, one line for each command, and an Error with no throw. Around it, the window classes write the static Faults.Trace, with its own format, switch and time stamp. A one-way bridge in TrayApp joins the two systems, and the test harness adds three more writers.

One theme in tokens, with dark modeGoodapp.css :root and one dark media rule

Each color, shadow and font is a token in app.css, except the 11 literals of S-G2. One prefers-color-scheme: dark rule sets each color and shadow token again (app.css:24-40). Components use only tokens. Most radii are literals (S-G9).

Each motion time and tray size is a tokenGoodI11 fixed in R1, I10 fixed in R2

The motion times are --t-* tokens of motion.css. The tray sizes are tokens of tray.css, and orchTray.sizes() reports them to the windows. Tests: Motion_times_are_tokens, Tray_sizes_are_tokens, Tray_window_sizes_come_from_the_page.

Data gives token names, not colorsGoodUi.Look and the template schema give a tone name

Ui.Look returns a token name such as "pending" (src/Orchestrator.Web/Ui.cs:107,169), and the component writes var(--pending). The template schema limits a tone to an enum (templates/_spec/view.schema.json, $defs.tone). A template cannot put a raw color in the page.

The step contract is a data hookGooddata-motion and --motion-wait, checked on both sides

A step is data-motion on an element plus --motion-wait in the sheet (motion.css:37-41, tray.css:139-145). The wait rule stays next to the motion rule. MotionRegistryTests checks both sides.

Reduced motion keeps the end eventsGoodI13 fixed in R1: 1 ms tokens

The prefers-reduced-motion rule in motion.css sets each duration token to 1 ms. The test Reduced_motion_sets_each_duration_token_to_1ms checks it.

What the old design teaches

Before the redesign, the tray had four native windows: the widget, its shadow, the home ball and the side badge. The handover of session V lists the main reason for its faults: "four windows that must look like one". The shadow, the ball and the widget show at the same time and must join without a gap.

The rule from this: split by what shows at the same time. The panel and the badge never show at the same time, and the dock has no object that flies from one to the other (spec: the panel folds into the ball, the ball pops out, then the badge slides in). So two windows for them do not have the "look like one" problem.

Short look

  • Vue <Transition>: six classes for enter and leave; Vue detects the end event itself.
  • Angular: animate.enter and animate.leave add CSS classes; it waits for the longest animation, with a 4 s fallback.
  • Framer Motion: AnimatePresence with exit and key; modes sync, wait, popLayout.
  • Adobe Spectrum: duration and ease tokens as CSS variables.
  • MudBlazor: no motion system; Duration and Delay are C# parameters, the same problem as ours. Blazor has no built-in transitions.
  • Page moves: none of these libraries has its own route transition API.

Closest to us

Web Awesome 3. It has CSS keyframes and tokens, one small JS helper that adds a class and waits for getAnimations(), and a state class from the host. Our orchMotion.settle is almost the same helper. Next are Radix and Headless UI: the state is in the framework, the motion is in CSS, and one presence part waits.
