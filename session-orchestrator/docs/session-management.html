Session Management Options

How the orchestrator starts, shows and controls its sessions in the Claude Code app. One proposal for each tab, each with the same worked example. The last tab gives the recommendation and the open questions.

Requirements

#RequirementWeight
R1The orchestrator starts sessions when it needs them, with the settings and context they needMust
R2The sessions use the orchestrator toolsMust
R3The orchestrator controls, adds and archives themMust
R4They show in the app, so you can read their data and talk to themMust
R5They show as attached child sessionsWish. The visual part is the least important
R6One writer at a time (the lease)A limitation that we found. Review it later
—Use the existing tools, with our templates and workflow on top. No own harness, no fight with the enginePrinciple

Findings

#FindingSource
F1start_session makes an attached session with its title. It works only in a turn that you started, or from a card that you click. So each of your messages gives one levelProbe tree
F2The supervisor (claude -p) starts sessions at any time and depth. claude --desktop --resume puts them in the sidebar with their titleRun 1
F3Only the app sets the parent link, when it creates the session. No CLI flag or API sets it later. A file edit is overwritten while the app runs. Request #106214 is openResearch, file test
F4orch enable lets any session join the store and get the tools, with no typed commandProbe tree
F5A message from another session is plain text. It cannot run a command, and it cannot let that session start childrenProbes
F6The store id of an app session (CLAUDE_CODE_SESSION_ID) is not its app id (CLAUDE_CODE_HOST_SESSION_ID)Probe tree
F7The import starts the app process. The session then runs in the app with the lease live. When the app closes, the supervisor continuesRun 1

The worked example on each tab

You ask for "run 2": a root orchestrator with three streams, D1, D2 and B1. While you are away, D1 asks a question, and B1 needs one sub-session for a spike. You come back, talk to D1 directly, and the run ends. Each proposal tab follows these steps and shows what you see in the sidebar.

A. Supervisor first

recommendedR1 R2 R3 R4R5 noone start path

The supervisor starts each session with claude -p and the title (-n). After the first good turn, it imports the session into the app with claude --desktop --resume. The store keeps the real tree. I add Remote Control and the sidebar group with the app tools.

  S-->>Sup: first turn done
  Sup->>App: claude --desktop --resume id
  App->>S: app process starts, lease live
  Me->>App: set_remote_control, move to group "Run 2"
  S->>Sup: spawn_child (D1, D2, B1): same steps, any time, any depth

Recommendation: A

A meets each must, works while you are away, and has one start path. Each behavior of the attachment except the visual tree already exists in our store, or is a small addition. When the app adds a parent flag (#106214), A gets the real tree with one more argument on the import.

Use start_session only for a session that you want next to this chat, for example a probe.

Do

  1. Store the app id of each session.
  2. Make the import reliable: confirm it, and make orch open check turn.json.
  3. Add Remote Control after the import, orch archive --tree, and the cleanup of the old store sessions.
  4. Record the decision and the findings in plan.md and decisions.md.

Do not

  • Edit the app's session files.
  • Restart the app on purpose to make a change stick.
  • Use the app's private messaging channel to act as you.
  • Build our own harness.
  • Wait for the attachment before the next run.
