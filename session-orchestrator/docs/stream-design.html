Work streams

A work stream is one area of work with one goal, one owner session and one integration branch. Its parts run in a fixed workflow: design, approve, code, review, integration, merge. The user approves the design, the plan and each merge. The framework starts, tracks and reports the rest. Status: proposal. The tab "Open questions" lists the items that wait for the user.

A work stream owns its parts

flowchart TD
  U([User]) -->|brief| R[Top root]
  R -->|brief| S[Stream root C]
  S -->|brief| C1[C1 design]
  S -->|brief| C2[C2 code]
  S -->|brief| C3[C3 integration]
  C2 -.->|message| S
  S -.->|probe brief| P[C2a probe]

A part id is the letter of its work stream and a number: C1, C2. A probe of a part adds a letter: C2a. One part has one decision group, one branch and one PR.

Rules of a work stream

  • The user starts a work stream. A session never starts a work stream by itself.
  • The stream root starts each part. A part never starts a session.
  • Each part gets a short brief and a session kind. The kind skill holds the steps.
  • The user approves the design and the plan before the first code part starts.
  • Only the user word merges a PR. orch merge does the merge.

  participant V as Review part
  participant U as User

  S->>V: brief, PR link
  V->>S: report, verdicts
  S->>P: send changes
  P->>S: report done
  S->>U: report working, PR ready
  U->>S: review approve, merge
  S->>S: orch merge

Merge rules

  1. Merge only when the user says so. The brief of the work stream can allow merges of part PRs into the integration branch.
  2. Merge only with orch merge <pr>. A hook blocks gh pr merge.
  3. If a PR carries a default decision with no approve review, orch merge refuses it.
  4. Merge the integration PR into the base only on the user word, never by a brief.
  5. Archive a part after its PR is merged or closed.

Expectations

  • A work stream does not run unattended to the end. It stops at each gate of the user.
  • A default decision does not stop a work stream. It stacks a branch for a later review.
  • The review part finds problems. It does not prove that the code is correct.
  • The live test runs only in the scratchpad, with its own store and port.
