Session orchestrator · design C1

Streams

A stream is a group of work. It is a stream id on sessions and events, not a store record. Each session decides if it works alone or starts children, and how deep. The creator of a session sets its kind. A workflow is a sequence of steps, with loops. Each step defines its input, output, actor and approval. The first workflow is planning. Status: all questions have answers. The design waits for the approval of the user.

A stream id groups a tree of sessions

  U([User]) -->|starts, kind orchestrator| A["Session A
stream = C"]

general · stream = C"]
  A -->|brief| D["Task C2

  D -->|brief| E["Task C2a

Session A starts children because its creator asked for an orchestrator. Task C2 also starts children: that is its own decision. Session G works alone.

Rules

  • Any session can start children. Nothing forces it to.
  • The session decides the depth of its tree.
  • The creator of a session sets its kind. Nothing enforces the kind for now.
  • A child gets the stream id of its parent, unless the brief gives another id.
  • The parent decides how it reviews and merges the work of its children. For now the user reviews all PRs.

A workflow is a sequence of steps, with loops

flowchart TD
  S1[1 Read the goal and the docs] --> S2[2 Ask one question]
  S2 --> S3[3 Answer · human]
  S3 --> S4[4 Record the answer]
  S4 -->|questions open| S2
  S4 -->|no open questions| S5[5 Write the spec]
  S5 --> S6{6 Approve the spec · human}
  S6 -->|change| S2
  S6 -->|approve| S7[7 Propose the next tasks]

This is the draft of the planning workflow, the first workflow. It follows the work of this C1 session.

Each step defines its parts

FieldMeaningExample
instructionsWhat to do in the step"Ask one question in the full format"
inputWhat the step needsThe brief, an open question
outputWhat the step makesA decision row, a spec
actorWho does the step: an agent or a humanhuman
approvalIf the step needs an approval, and who gives itThe user, the orchestrator
strategyHow the approval worksrequired, skippable, ignored
messagesWhen the step sends a message, and to whomA report to the orchestrator
nextThe next step, or a loop back by the outputchange → step 2

A step can start a child session that runs its own workflow. So a workflow can run in one session or across a tree of sessions.

Draft of the planning workflow

workflow: planning

How an orchestrator splits work

flowchart TD
  G[Goal in the brief] --> S[Split into tasks]
  S --> Q{Question for the user?}
  Q -->|yes| A[Ask in chat or with ask_user]
  A --> S
  Q -->|no| B[One brief for each task, same stream id]
  B --> C[spawn_child for each task]
  C --> W[Relay questions, collect reports]
  W --> R[Report to the parent or the user]

Steps

  1. Read the goal and the scope in the brief.
  2. Split the goal into tasks. One task is the work of one session.
  3. Give each task an id: the stream letter and a number, such as C1.
  4. Write one short brief for each task.
  5. Start each task with spawn_child.
  6. Relay the questions of the children to the user.
  7. Collect the reports, then report to the parent or the user.

A task can split again with the same steps. The skill orch:orch-brief holds the brief rules.

Find all work of a stream

# each event of stream C, from any session at any depth
orch events --stream C
# the sessions of stream C, with their state
orch sessions --stream C

Both commands are C2 proposals. The event stream can group and count by stream later, so a central record is not necessary.

How the user approves

The place of an approval depends on the type of work. The user can approve in the orchestrator or in the session that does the work. The approval rules belong to the review workflow on the roadmap.
