HOW IT WORKS

Result first: the message fields have a real schema (JSON Schema). The views and the components have no schema file. Their shape exists only in C# records and Razor code. No parser finds templates in a folder: the code opens a fixed list of 10 names.

Inside a view.json

One file for each kind. document is the Open view. preview drives the card and the stream row together.

// templates/question/view.json
{
  "label": "Question", "icon": "q", "tone": "new",      // head of each surface; tone = a color token
  "document": {                                        // the Open view
    "title": ["{{question}}"],                         // title templates: the first one with all its fields wins
    "facts": [                                         // short values in one table
      { "field": "risk", "label": "Risk", "as": "pill",
        "tones": { "low": "done", "medium": "pending", "high": "failed" } },
      { "field": "defaultOption", "label": "Default" }
    ],
    "blocks": [                                        // one block for each field, in this order
      { "field": "context", "label": "Context" },
      { "field": "snippet", "label": "Snippet", "as": "code" },
      { "field": "options", "label": "Options", "as": "chips", "mark": "defaultOption" },
      { "field": "recommendation", "label": "Recommendation", "as": "well" }
    ]
  },
  "preview": {                                         // the card and the stream row
    "title": ["{{question}}"],
    "line":  ["{{recommendation}}", "{{context}}"],    // line 3 of the stream row
    "well":  [{ "field": "recommendation", "label": "Recommendation" },
              { "field": "context", "label": "Context" }],   // the first field with a value
    "chips": { "field": "options", "mark": "defaultOption" },
    "pill":  { "field": "risk", "as": "pill", "tones": { ... } }
  }
}

The parts of a field spec

KeyMeaningExample
fieldThe schema field to show"context"
labelThe label above the block or left of the fact"Context"
asThe component. Default: text"chips"
markA field whose value is marked in the chips"defaultOption"
tonesA color token for each value of a pill{"high": "failed"}
toneA color token for the whole block"failed"
renderA field whose value names a render file. The block shows that render"kind" (notice)
maxThe maximum count of items in a preview list4

A title or a line is a list of templates. {{field}} puts in a value. {{#field}}…{{/field}} shows its content only when the field has a value. {{render:field}} puts in the first line of the render that the field names.

Target: one format, one check and one place for each layer

  1. Spec files. templates/_spec/meta.schema.json and view.schema.json. Each file points to them with $schema, so the editor checks it as you type.
  2. Component catalog. templates/_spec/looks.json lists each component and the field types that it accepts. The view schema takes its as values from it.
  3. One Razor file for each component in Ui/Looks/. This page renders the real components with bUnit, so the JavaScript copy goes away.
  4. Registry. A folder scan of the core and the added templates (tab Registry).
  5. One check. orch template check and the unit tests use the same spec files.

TEMPLATE REGISTRY

Goal: a new template needs only files: schema.json, meta.json, view.json and example.json. No C# change. Today TemplateSet reads only the 10 names in Kinds.All, so a new folder has no effect.

Two kinds of templates

KindExamplesFolderWhat a file change can do
Corequestion, answer, review, report, plan, brief, notice, ack, message, update<home>/templates/Change the fields, the view and the renders. The behavior (defaults, stack, first answer wins, spawn) stays in C#. A core template cannot be removed.
Addedfor example risk-note, test-result, design-review<store>/templates/ (Q1)All of it. A session posts it, the stream checks it against the schema, the receiver gets it, the UI shows it, the user acks it.

Folder of a template

<store>/templates/ the added templates

schema.json required: the fields (JSON Schema, object, no additional properties)The plugin tool uses it as its input schema. The stream rejects a body that does not match.
meta.json required: purpose, from, to, needs, replies, card, turn, tooltype must be the folder name. New keys: turn (a receiver session gets it as a turn; default true when to has a session) and tool (the plugin tool to register).

render/session.md optional: the text that a receiver session getsWith no render, the session gets the preview title and the fields as a list.

Add a template

  • Write the folder, for example in the scratchpad. orch template new test-result writes a skeleton.
  • orch template check <folder> runs the checks below.
  • orch template add <folder> checks again and copies the folder to <store>/templates/test-result/.
  • The supervisor sees the change and loads the template set again. The UI shows the kind at once.
  • Sessions get the tool mcp__orch__<tool.name> at the next plugin load (hot reload).

Remove a template

Only an added template can be removed. Old messages of that kind stay in the stream. The UI shows them with the fallback model: each field as a text block. orch template add of the same folder restores the look.

OPEN QUESTIONS

Answer in the chat of the F1 session. The recommendation is in bold. The answers go into docs/decisions.md and on this page.

  1. Q1. Where do added templates live? In <store>/templates/, the store folder ~/.orch/templates, or <home>/templates/ in the repository.
    Answer (user): in the store, one folder for each template, the same layout as templates/. The store location is a separate discussion. How users make their own templates comes later, after a full working version.
  2. Q2. Can an added template replace a core template? Only its view.json, all files, or no.
    Answer (user): yes. A store template with a core name replaces the core template. That is the way to customize a core kind. It is not the focus now: the consumer customization comes at the end.
  3. Q3. Which surfaces add and remove? CLI to add and remove, API and plugin tool to list, or also API add and remove for a later UI page.
    Answer (user): define the local file format, a library interface (ITemplateStore), the CLI, and one local implementation. The CLI calls only the interface. A later store (Notion, a cloud bucket) is a new implementation of the same interface. No HTTP API and no plugin tool now.
  4. Q4. The look changes X1 to X10 and the notes of each kind. Do all, or name the ones to skip or change.
    Answer (user): no look changes now. The user did not review the looks yet. The system matters: the app must show each kind exactly as this page shows it. A change of a view.json to make the app and the page match is allowed. X1 to X10 stay proposals.
  5. Q5. A markdown look? Yes, with the Markdig package, or no: keep plain text.
    Answer: not now. It is a look change (Q4).
  6. Q6. Spec files, component catalog and one Razor file for each component (tab How it works, target). Yes, all three, only the spec files, or no.

The full document and the preview of each kind, with the data of templates/<kind>/example.json. The page reads each view.json: the same spec that the C# model Views uses.

Not shown. The actions (Accept, Other, Approve, Change, Got it, Reply) come from meta.json card and stay as they are in the A4 views. The forms to make a message are a later part.
