Proposal · generic engine

Pattern Engine

One engine selects patterns, composes them and evaluates the result. A domain pack sets the subject. To change the subject from shapes to UI or code, change the pack. The core does not change.

Two patterns match

No pattern matches

Select the nearest pattern. List each change from it. Verify. Write a proposed pattern file.

The swapFrom shapes to UI to code: what you write for each new pack›
  1. Copy domains/shapes/ to the new name.
  2. Write instructions.md for the subject.
  3. Write the four adapter functions.
  4. Write the patterns in the same template. Write the asserts for each pattern.
  5. Write about 20 hand cases. Run the generator for the rest.
  6. Run the eval. Compare the scores with the shapes scores.

If the new pack scores much lower than shapes, examine the pack first. The core passed its tests on shapes.

Element · pattern definition

One pattern file

Front matter for the machine, sections for the agent. The core owns all fields. The pack owns only the content.

domains/shapes/patterns/house.md
---
id: house
kind: composition  # primitive|composition|scene
level: 2
status: stable       # proposed|trial|stable
use_when:
  - The request names a house, a home or a hut.
do_not_use_when:
  - Taller than 2× its width. Use tower.
variants:
  - id: plain
    when: No extra part is named.
  - id: chimney
    when: The request names a chimney or smoke.
parts:
  - { ref: body,    count: 1 }
  - { ref: roof,    count: 1 }
  - { ref: door,    count: 1 }
  - { ref: window,  count: "0..4" }
  - { ref: chimney, count: 1, only: chimney }
params:
  door_fill: { default: brown }
related: [street, tower]
asserts: asserts/house.yaml
---
## Intent
One house, seen from the front.

## Rules
- Do: the roof base is as wide as the body.
- Do not: put the door above the body bottom.

## Rationale
A child reads this shape as "house" at once.

Edges

Four kinds of link

parts"is made of". house → roof. The agent follows it in the divide step
variants"a form of". house → chimney. Each variant has its own trigger
do_not_use_when → id"use that one". house → tower. Separates near patterns
related"close to". Two-way. The no-fit step uses it to find the nearest

The graph builder fails the build for a link to a missing pattern, a parts cycle, or a level that is not lower than its parent.

Worked example · composition

“Draw a street with three houses. The middle house has a red door and a chimney.”

1
Index"street" matches street.use_when. "houses" matches house.use_when
2
SelectTop pattern: street, variant row. Its parts: house × 1..n
3
DivideThree house parts. Ask again for each: 1 and 3 are plain. 2 is chimney with door_fill: red
4
Divide againEach house → body, roof, door, window (+ chimney). Each part → rect or triangle
5
ComposeWrite the SVG from the bottom up. Follow instructions.md and the Rules of each pattern
6
VerifyAdapter: parse → run street.yaml and house.yaml × 3 → lint. All pass on attempt 1

Validation · v1 on shapes

Do we need 100 golden fixtures?

No. Use about 20 golden files, and only to test the graders.

A drawing has many correct forms, so a fixed golden output fails good results. Check properties instead: the trace tree and the asserts. The graph gives the expected tree, so a generator makes most cases with no hand work.

When v1 "works"

Proposed targets. We set the real ones after the first baseline.

MetricGraderTarget
Selection accuracy (pattern + variant)selection · deterministic≥ 90%
Structure pass@1structure · deterministic≥ 85%
pass^5: all 5 runs of a case passall graders≥ 70%
Near-miss accuracyselection≥ 80%
No-fit precision: no forced patternselection + trace≥ 80%
Rubric scorejudge · LLM≥ 1.5 / 2
Judge agreement with your labelscalibration≥ 80%

With 400 runs, a pass rate near 85% has a 95% interval of about ±3.5 points. That finds a drop of 10 points with confidence. To find smaller drops, add cases.
